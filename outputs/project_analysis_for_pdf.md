# 🏢 EMS 프로젝트 완전 분석 가이드

> 이 문서는 프로젝트의 모든 것을 **비전공자도 이해할 수 있도록** 쉽게 풀어 설명합니다.

---

## 1. 프로젝트를 한 줄로 요약하면?

> **"독일에 있는 Honda 연구소 건물의 6년치 전기·난방·냉방 데이터를 분석해서, AI가 자동으로 에너지를 관리해주는 플랫폼을 만드는 프로젝트"**

비유하자면, 건물 전체에 **81개의 전기 요금 측정기(계량기)** 를 붙여놓고 6년 동안 15분 단위로 모든 에너지 사용량을 기록한 "건물의 건강기록부"를 분석하는 것입니다.

---

## 2. 이 프로젝트는 왜 하나요? (비즈니스 목표)

| 목표 | 설명 |
|------|------|
| **대상 고객** | 데이터 분석 역량이 부족한 **중소 제조공장** |
| **핵심 가치** | 공장 관리자가 "이번 달 전기 왜 이렇게 많이 나왔어?" 같은 **자연어 질문**을 하면 AI가 자동 분석·답변 |
| **최종 목표** | 에너지 이상 감지, 비용 절감 제안, 자동 보고서 생성까지 해주는 **AI 챗봇 플랫폼** |

## 4. 데이터는 어떻게 흘러가나요? (데이터 파이프라인)

### 4.1 데이터의 정제 단계

원본 데이터가 최종 분석용 데이터가 되기까지 **4단계** 를 거칩니다.

```
🔴 Raw           🟡 Corrected          🟢 Corrected Resampled      🔵 Reduced
가공 전 원시  ──▶  오류 보정 완료  ──▶   시간 간격 통일          ──▶  81개→4범주
데이터                                 (15분 / 1시간)               압축 합산
```

| 단계 | 비유 | 설명 |
|------|------|------|
| **Raw** | 환자의 심전도 원본 기록 | 센서가 그대로 기록한 값. 노이즈, 오류 포함 |
| **Corrected** | 의사가 잡음을 걸러낸 기록 | 부호(+/-) 통일, 결측 보정, 시간 오차 정렬 |
| **Corrected Resampled** | 15분/1시간 간격으로 정리한 기록 | 이 프로젝트의 **주 분석 대상** |
| **Reduced** | 건강 요약 리포트 | 81개 계량기를 전기·난방·냉방·기상 **4개로 요약** |

### 4.2 데이터베이스 구조

```
TimescaleDB (PostgreSQL 확장)
├── ems.full_meter                    ← 81개 계량기의 "프로필 카드"
├── ems.cr_measurement_15min          ← 15분 간격 측정값 (원본 마트)
├── ems.cr_measurement_1h             ← 1시간 간격 측정값 (원본 마트)
├── ems.reduced_measurement_15min     ← 4대 범주 합산 뷰 (15분)
└── ems.reduced_measurement_1h        ← 4대 범주 합산 뷰 (1시간) ★ ML 학습용
```

> **[참고] TimescaleDB**란?
> PostgreSQL(관계형 DB)에 **시계열 데이터 전용 기능**(빠른 시간순 조회, 자동 파티셔닝)을 추가한 확장입니다. 쉽게 말해 "시간 데이터에 특화된 SQL 데이터베이스"입니다.

### 4.3 Reduced View의 4대 범주

81개 계량기를 **건물 전체 관점**에서 4개 카테고리로 묶은 것입니다.

| 범주 | Subcategory | 뜻 | 포함 계량기 |
|------|-------------|-----|------------|
| **electricity** | total | 건물 전체 전기 소비 | V.Z81, V.Z82 등 변압기 계량기 6개 |
| | pv | 태양광 발전량 | V.Z84 등 PV 계량기 4개 |
| | chp | 열병합발전 전기 출력 | H1.Z20 (또는 H1.ZE20) |
| **heating** | total | 총 난방열 | H1.W11 (가스보일러) |
| | chp_heat | CHP에서 나온 열 | H1.W12 |
| **cooling** | total | 총 냉방열 | V.K21 |
| | cool_elec | 냉각 설비 전기 소비 | H1.Z16 등 5개 |
| **weather** | Ta / Igm | 외기온 / 일사량 | WeatherStation.Weather |

## 5. 프로젝트의 핵심 발견

### 5.1 데이터 품질

| 발견 | 의미 |
|------|------|
| 에너지 미터 결측률 **0.03%** | 거의 완벽한 데이터. 다만 결측이 0%인 이유는 **장애 구간을 과거 데이터 복사**로 채웠기 때문 |
| 기상 데이터 결측률 **2.35%** | 특히 2018년에 7.11% 집중. DWD(독일기상청) 데이터로 보완 필요 |

### 5.2 설비 변경 이벤트 (Regime)

6년 동안 건물 설비가 **6번 크게 바뀌었습니다.** 이 때마다 에너지 사용 패턴이 달라지기 때문에, 데이터를 구간별로 나눠서 분석해야 합니다.

| 시기 | 이벤트 | 비유 |
|------|--------|------|
| 2019-02 | CHP 제어 방식 변경 | 보일러를 껐다 켰다 → 세기 조절로 변경 |
| 2019-06 | PV(태양광) 1차 설치 | 지붕에 태양광 패널 소규모 설치 |
| 2020-03 | COVID-19 | 재택근무 시작 → 건물 전력 소비 급감 |
| 2020-06 | PV 2차 증설 (749kWp) | 태양광을 풀 규모로 확장 |
| 2020-09 | 계량기 교체 | 핵심 전기 미터 2개 교체 (H2.Z35→Z351) |
| 2023-06 | 난방 현대화 | 난방 시스템 업그레이드 |

> **⚠️ 중요:** 모델 학습 권장 구간은 **Regime 5 (2020-09 ~ 2023-06)** 입니다.
> 설비 교체가 완료되고 안정적으로 운영된 약 2.75년 구간입니다.

### 5.3 Regime 구간 분할 상세

| 구간 | 기간 | 주요 특성 |
|------|------|-----------|
| Regime 0 | 2018.01 ~ 2019.02 | PV 없음, CHP On/Off 방식 |
| Regime 1 | 2019.02 ~ 2019.06 | CHP 연속 모듈레이션 |
| Regime 2 | 2019.06 ~ 2020.03 | PV Phase1 가동 |
| Regime 3 | 2020.03 ~ 2020.06 | COVID 영향 (부하 급감) |
| Regime 4 | 2020.06 ~ 2020.09 | PV Phase2 풀 용량 |
| **Regime 5** | **2020.09 ~ 2023.06** | **계량기 교체 완료, 안정 운영 → 모델 학습 권장** |
| Regime 6 | 2023.06 ~ 2024.01 | 난방 현대화 (CHP 하절기 가동) |

## 7. ML 모델 학습 결과

### 7.1 두 모델이 예측하는 것

> **"다음 1시간 뒤에 이 건물이 전력망(Grid)에서 얼마나 전기를 가져올 것인가?"** 를 예측합니다.

### 7.2 사용한 피처(입력 변수) 19개

| 종류 | 피처 | 쉬운 설명 |
|------|------|-----------|
| **달력** | hour, dayofweek, month, is_weekend | 지금 몇 시? 무슨 요일? 주말? |
| **주기 인코딩** | hour_sin/cos, month_sin/cos | "23시와 0시는 가깝다"를 AI가 이해하게 변환 |
| **기상** | temp_c, solar_wm2 | 바깥 기온, 햇빛 세기 |
| **Lag(과거값)** | lag_1h ~ lag_168h | 1시간 전 / 2시간 전 / ... / 1주일 전 소비량 |
| **Rolling(이동평균)** | roll_mean_24h, roll_std_24h, roll_mean_168h | 최근 24시간/1주일 평균 소비 추세 |

### 7.3 성능 비교

| 지표 | LightGBM | LSTM | 설명 |
|------|--------:|-----:|------|
| **MAE** | **38.78 kW** | 43.06 kW | 평균적으로 38~43kW 정도 오차 (피크 600kW 대비 약 8%) |
| **RMSE** | **60.12 kW** | 64.58 kW | 큰 오차에 더 가중치를 둔 지표 |
| **MAPE** | **59.87%** | 63.56% | 야간 저소비 구간 때문에 수치가 왜곡됨 |
| 학습 시간 | ~10초 | ~5분 | LightGBM이 훨씬 빠름 |

> **💡 참고:** MAPE가 60%로 높아 보이지만, 이는 야간에 전력이 3kW까지 떨어지는 구간에서 분모가 너무 작아지기 때문입니다. 실질적으로 **MAE 38kW는 피크 대비 약 8~10% 오차**로, 에너지 관리 목적으로는 실용적인 수준입니다.

### 7.4 LightGBM 피처 중요도 Top 10

| 순위 | 피처 | 중요도 | 해석 |

| 1 | solar_wm2 (일사량) | 1,069 | 냉방 부하와 밀접 |

## 10. 핵심 용어 사전

### 10.1 에너지 / 전기 용어

| 용어 | 쉬운 설명 | 비유 |
|------|-----------|------|
| **계량기 (Meter)** | 에너지 사용량을 측정하는 기기 | 집에 있는 전기 계량기와 같음 |
| **유효전력 (P)** | 실제로 일을 하는 전력 (W) | 물을 끓이는 데 실제 쓰인 열 |
| **무효전력 (Q)** | 자기장 유지용으로 왔다 갔다 하는 전력 (var) | 물을 끓이진 않지만 냄비를 흔들어대는 힘 |
| **역률 (PF)** | 전력을 얼마나 효율적으로 쓰는지 (0~1) | 1이면 100% 효율. 0.8이면 20%가 낭비 |
| **유효전력량 (W)** | 시간 동안 쌓인 유효전력 (kWh) | 전기요금의 기본 단위 |
| **무효전력량 (WQ)** | 시간 동안 쌓인 무효전력 (kvarh) | 역률이 나쁘면 전력회사가 과태료를 매기는 기준 |
| **Grid (전력망)** | 한전 같은 외부 전력망 | 수도꼭지에서 나오는 물 = 외부 전기 |
| **PV (Photovoltaic)** | 태양광 발전 시스템 | 지붕의 태양광 패널 |
| **CHP** | 열병합발전. 가스로 전기+열 동시 생산 | 하나의 엔진으로 전기도 만들고 난방도 하는 시스템 |
| **kWp** | 태양광 패널의 최대 발전 용량 | 749kWp = 가장 좋은 조건에서 749kW 생산 가능 |
| **지상 부하** | 모터 등 무효전력을 소비하는 기기 | 역률을 깎아먹는 쪽 |
| **진상 부하** | 콘덴서 등 무효전력을 보상하는 기기 | 역률을 올려주는 "해독제" |

### 10.2 데이터 / DB 용어

| 용어 | 쉬운 설명 |
|------|-----------|
| **시계열 데이터** | 시간 순서대로 나열된 데이터. 주가, 온도, 전력 같은 것 |
| **해상도 (Resolution)** | 데이터를 얼마나 자주 기록하는지. 15min = 15분마다 |
| **결측 (Missing/Null)** | 데이터가 빠져 있는 구간. 센서 고장이나 통신 장애로 발생 |
| **뷰 (View)** | DB에서 복잡한 쿼리를 이름 붙여 저장한 "가상 테이블" |
| **DDL** | 테이블이나 뷰를 만드는 SQL 명령어 (CREATE, ALTER 등) |
| **멱등성** | 같은 작업을 여러 번 실행해도 결과가 같다는 뜻 |
| **Hypertable** | TimescaleDB의 시간별 자동 파티션 테이블 |
| **Gateway** | 여러 센서의 데이터를 수집해서 서버로 보내는 장치 |
| **Gap Filling** | 결측 구간을 채우는 것. 이 프로젝트에서는 과거 데이터 복사 방식 |

### 10.3 ML / AI 용어

| 용어 | 쉬운 설명 |
|------|-----------|
| **LightGBM** | MS가 만든 트리 기반 ML 모델. 표 데이터에 매우 강력하고 빠름 |
| **LSTM** | 시계열의 과거 패턴을 "기억"하는 딥러닝 모델 |
| **피처 (Feature)** | 모델에 넣는 입력 변수. "힌트"라고 생각하면 됨 |
| **타겟 (Target)** | 모델이 예측해야 할 정답. 여기서는 "다음 1시간 Grid 전력" |
| **Lag 피처** | 과거 시점의 값을 현재 입력으로 넣는 것 |
| **Rolling 피처** | 최근 N시간의 평균/표준편차. 추세 파악용 |
| **MAE** | 예측값과 실제값의 평균 오차. 38kW = 평균 38kW 빗나감 |
| **RMSE** | 큰 오차에 더 벌점을 주는 지표 |
| **MAPE** | 오차의 백분율 평균. 실제값이 0에 가까우면 왜곡됨 |
| **Early Stopping** | 과적합 방지를 위해 검증 성능이 나빠지면 학습 중단 |
| **과적합** | 학습 데이터만 잘 맞추고 새 데이터에서 성능 저하 |
| **MinMaxScaler** | 모든 값을 0~1 범위로 변환. 단위가 다른 피처 통일 |
| **Huber Loss** | MSE와 MAE의 중간. 이상치에 덜 민감한 손실 함수 |
| **Sliding Window** | 24시간치를 한 묶음으로 넣어 다음 1시간 예측 |
| **MLflow** | ML 실험 추적 도구. 어떤 설정이 최선인지 기록 |
| **Text-to-SQL** | 자연어 → SQL 자동 변환. "전기 사용량?" → SELECT SUM(...) |

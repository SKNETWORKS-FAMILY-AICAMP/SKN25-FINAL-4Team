# EMS 피처 명세

**갱신일:** 2026-05-08  
**범위:** 전처리 결과에서 모델 입력, 이상탐지, live replay 평가로 전달되는 feature 생성 기준. 계량기 metadata, ontology helper, 저장 계층, 시간 누수 방지 규칙을 연결한다.

---

## 1. 목적

이 문서는 EMS 분석에서 feature를 생성할 때 사용하는 공통 계약을 정의한다. Feature 생성은 DB 또는 Parquet에서 측정 row를 읽어 계산하지만, 대상 meter set과 redundancy 처리 기준은 ontology helper와 meter metadata 명세를 통해 결정한다.

피처 명세는 다음 문서와 연결된다.

| 기준 문서 | 담당 범위 |
|---|---|
| `docs/specs/데이터_계약.md` | 분석 입력 row grain, timestamp, measurement, quality 기준 |
| `docs/specs/계량기_메타데이터.md` | meter domain, role, equipment group, redundancy, 부호 규약 |
| `docs/specs/프로젝트_개요.md` | 기준 데이터, 분석 범위, live replay 평가 원칙 |
| `docs/specs/온톨로지_스키마.md` | ontology artifact와 meter relationship schema |

---

## 2. 기본 원칙

1. Feature 생성의 기본 입력은 `docs/specs/데이터_계약.md`의 long format 계약을 따른다.
2. 초기 feature baseline은 `15min` 해상도를 기본으로 한다.
3. 장기 추세와 보고 지표 feature는 `1h` 해상도를 사용할 수 있다.
4. `1min` feature는 기간, meter, measurement 범위를 제한한 event-level 분석에만 사용한다.
5. Measurement row 자체를 RDF로 변환하지 않는다.
6. Ontology는 meter set, group, role, redundancy, visualization context 조회에만 사용한다.
7. DB와 Parquet 접근 위치는 `docs/specs/데이터_계약.md`의 저장소 경계를 따른다.
8. 모델 입력 직전까지 long format을 유지하고, wide format 전환은 명시된 feature set 단위로 수행한다.
9. Live replay feature는 현재 tick 이전 데이터만 사용한다.
10. Feature 계산 결과는 원천 row를 대체하지 않고 별도 lineage를 가진 산출물로 관리한다.

## 3. Feature 입력 계약

### 3.1 필수 입력 column

Feature 생성 함수는 다음 column을 포함한 long format 입력을 받는다.

```text
(ts, meter_urn, measurement, value, resolution_code, source_file)
```

| Column | 기준 | 처리 규칙 |
|---|---|---|
| `ts` | UTC `timestamptz` | 정렬 기준. 기간 조건은 `[start_ts, end_ts)`를 사용한다. |
| `meter_urn` | `ems.full_meter`, ontology meter individual | feature 대상 meter set 검증에 사용한다. |
| `measurement` | `ems.full_measurement_definition` | feature family와 단위 검증에 사용한다. |
| `value` | 원 DB 값 | 단위 변환 없이 입력하고 파생 feature에서만 변환한다. |
| `resolution_code` | `1min`, `15min`, `1h` | table 또는 query context에서 명시한다. |
| `source_file` | source lineage | 결측, 중복, row balance 확인에 사용한다. |

### 3.2 권장 보조 column

전처리 단계에서 다음 column을 추가할 수 있다.

| Column | 기준 | 설명 |
|---|---|---|
| `unit` | measurement dictionary | 동일 feature family 내 단위 혼합 방지 |
| `measurement_family` | measurement definition | 전기, 열, 기상 계열 분리 |
| `meter_domain` | ontology 또는 meter metadata | `electricity`, `thermal`, `weather` |
| `meter_role` | ontology 또는 meter metadata | `consumption`, `production`, `thermal_flow`, `weather` |
| `equipment_group` | ontology 또는 meter metadata | 설비·계통 group |
| `building_code` | ontology 또는 meter metadata | building 또는 zone prefix |
| `quality_flag` | quality validation | 결측, 중복, 비정상 부호, lineage mismatch 표시 |

## 4. 저장 계층별 feature 입력 기준

| 해상도 | 기본 저장 계층 | feature 사용 기준 | 비고 |
|---|---|---|---|
| `15min` | PostgreSQL/TimescaleDB `ems.cr_measurement_15min` | 초기 feature baseline, 이상탐지 baseline, live replay 기본 tick | 기본값 |
| `1h` | PostgreSQL/TimescaleDB `ems.cr_measurement_1h` | 장기 추세, 일간·주간·월간 요약, 보고 지표 | baseline report에 적합 |
| `1min` | Parquet archive 또는 기존 partial DB table | event-level 상세 분석 | 기본 운영 분석 입력에서 제외 |

`1min` feature는 다음 조건을 충족할 때만 생성한다.

1. 기간 조건을 명시한다.
2. meter set을 ontology helper 또는 명시적 allowlist로 제한한다.
3. measurement set을 명시한다.
4. Parquet archive 또는 partial DB table 사용 여부를 기록한다.
5. 결과 산출물에 입력 source와 resolution을 기록한다.

## 5. Meter set 결정 기준

### 5.1 기준 API

분석 코드는 DB semantic view 또는 향후 확정된 분석 helper를 통해 meter set을 조회한다.

```python
from ems.ontology import EMSOntology

kg = EMSOntology.from_default()

server_primary = kg.get_feature_meter_set(
    group="server_power",
    domain="electricity",
    role="consumption",
    exclude_redundant=True,
)
```

Helper 조회 결과는 feature 생성 전에 log 또는 metadata로 남긴다.

### 5.2 기본 group별 meter set

다음 수량은 ontology helper 조회 기준이다.

| Group | Domain | Role | 전체 meter | 기본 aggregate meter | 기준 |
|---|---|---|---:|---:|---|
| `central_cooling` | `electricity` | `consumption` | 5 | 5 | 중앙 냉각기 전력 |
| `server_power` | `electricity` | `consumption` | 13 | 9 | redundant endpoint 제외 |
| `emission_lab` | `electricity` | `consumption` | 14 | 14 | 실험실·시험 설비 전력 |
| `pv` | `electricity` | `production` | 5 | 4 | redundant endpoint 제외 |
| `chp` | `electricity` | `production` | 2 | 1 | redundant endpoint 제외 |
| `local_cooling` | `electricity` | `consumption` | 5 | 3 | redundant endpoint 제외 |
| `weather_station` | `weather` | `weather` | 1 | 1 | 외생 변수 feature |

기본 aggregate meter는 `exclude_redundant=True` 기준이다. Redundant endpoint는 중복 합산 방지를 위해 aggregate에서 제외하되, 비교 feature에서는 별도 사용한다.

### 5.3 우선 feature group

초기 feature engineering은 다음 group을 우선 대상으로 한다.

1. `central_cooling`
2. `server_power`
3. `emission_lab`
4. `pv`
5. `chp`
6. `local_cooling`
7. `weather_station`

우선순위는 feature 설계와 검토 순서를 의미한다. 모델 가중치나 중요도 점수로 사용하지 않는다.

## 6. Redundancy 처리 기준

### 6.1 Aggregate feature

Aggregate feature에서는 redundancy pair의 redundant endpoint를 기본 제외한다.

```python
kg.get_feature_meter_set(
    group="server_power",
    domain="electricity",
    role="consumption",
    exclude_redundant=True,
)
```

적용 규칙:

1. Primary endpoint는 aggregate에 포함한다.
2. Redundant endpoint는 aggregate에서 제외한다.
3. Primary가 장기 결측 또는 품질 문제를 보이면 대체 규칙을 별도 문서화한 뒤 사용한다.
4. Primary와 redundant를 동시에 합산하지 않는다.

### 6.2 Comparison feature

Primary/redundant 비교는 별도 feature family로 생성한다.

| Feature family | 예시 | 설명 |
|---|---|---|
| `redundancy_abs_diff` | `abs(primary - redundant)` | 절대 차이 |
| `redundancy_signed_diff` | `primary - redundant` | 부호 있는 차이 |
| `redundancy_ratio` | `primary / redundant` | 분모 0 또는 결측 구간 제외 필요 |
| `redundancy_missing_overlap` | 동시 결측 여부 | source lineage 검토 후보 |
| `redundancy_disagreement_flag` | threshold 초과 여부 | 계량기 문제 후보 |

비교 feature는 설비 aggregate와 분리하여 저장한다.

### 6.3 Redundancy pair count

현재 ontology 기준 redundancy pair는 12개다. `server_power` group은 4개 pair를 가진다.

## 7. Domain 및 role별 포함·제외 규칙

| Feature 목적 | 포함 기준 | 제외 기준 |
|---|---|---|
| 전력 소비 aggregate | `domain=electricity`, `role=consumption` | `production`, `weather`, `thermal_flow` |
| 발전량 feature | `domain=electricity`, `role=production` | 소비 aggregate와 직접 합산 금지 |
| 열 계통 feature | `domain=thermal`, `role=thermal_flow` | 전력 consumption aggregate와 합산 금지 |
| 기상 외생 변수 | `domain=weather`, `role=weather` | energy aggregate 합산 제외 |
| building aggregate | 동일 building 내 목적별 role 분리 | role 혼합 합산 금지 |
| group aggregate | 동일 equipment group 및 role | 다른 group의 보조 설비 임의 포함 금지 |

Production meter는 부호 규약을 적용한 뒤 발전량 feature family에서 처리한다. Consumption aggregate와 production 값을 직접 합산하지 않는다.

Weather feature는 외생 변수로 사용하며 energy aggregate row에 포함하지 않는다.

## 8. Measurement family 기준

초기 feature family는 measurement code를 기준으로 다음처럼 분리한다.

| Feature family | Measurement 후보 | 처리 기준 |
|---|---|---|
| `electricity_power` | 전력 관련 measurement | role별 aggregate와 rolling 통계 |
| `thermal_flow` | 열·냉방 관련 measurement | 계통별 별도 feature |
| `weather_external` | 기온, 습도, 일사량 등 | lag, rolling, calendar interaction |
| `quality` | 결측률, 중복, source status | 모델 입력 보조 또는 filtering |
| `calendar` | timestamp 파생 | 누수 없이 생성 가능 |

Measurement code의 최종 사용 가능 여부는 `docs/specs/데이터_계약.md`의 measurement 식별자 기준을 따른다. `Pa`, `Quality`처럼 기본 분석 입력 제외 후보로 기록된 항목은 feature 계약에서도 기본 제외한다.

## 9. 시간 feature 및 rolling feature

### 9.1 Calendar feature

Calendar feature는 `ts`에서 직접 산출한다.

| Feature | 기준 |
|---|---|
| `hour` | UTC 또는 별도 보고용 local time 변환 기준 명시 |
| `day_of_week` | UTC 기준 우선 |
| `month` | UTC 기준 우선 |
| `is_weekend` | local calendar가 필요한 경우 변환 기준 기록 |
| `season` | 월 기준 파생 |
| `sin_time`, `cos_time` | 일주기 또는 주기성 encoding |

DST 구간 검증 전에는 local time feature를 모델 핵심 입력으로 고정하지 않는다.

### 9.2 Rolling feature

Rolling feature는 과거 방향으로만 계산한다.

| Feature | 기본 window 후보 | 규칙 |
|---|---|---|
| rolling mean | 1h, 6h, 24h, 7d | 현재 tick 이전 값만 사용 |
| rolling std | 6h, 24h, 7d | 최소 관측치 기준 필요 |
| lag value | 1 tick, 4 tick, 96 tick | 해상도별 tick 수 명시 |
| difference | 1 tick, 4 tick | 결측 구간 flag와 함께 사용 |
| cumulative energy | 일간, 주간 | 기간 경계와 timezone 기준 명시 |

Live replay에서는 scaler, imputer, threshold, rolling baseline을 학습 구간에서 fit한 뒤 replay 구간에는 transform만 수행한다.

## 10. Quality feature 기준

Quality feature는 모델 입력으로 직접 사용할지 여부를 실험별로 명시한다. 기본적으로 filtering과 report context에 우선 사용한다.

| Feature | 산출 기준 | 기본 용도 |
|---|---|---|
| `missing_flag` | `value IS NULL` | filtering, anomaly context |
| `missing_rate_window` | rolling NULL 비율 | drift 감시 |
| `duplicate_flag` | `(ts, meter_urn, measurement, resolution_code)` 중복 | 품질 제외 후보 |
| `source_status_flag` | `full_source_file.status` | 입력 제외 기준 |
| `row_balance_flag` | `full_file_load_balance` | lineage 검토 |
| `negative_consumption_flag` | consumption role에서 음수 | 품질 또는 계측 오류 후보 |
| `production_sign_flag` | production role 부호 규약 | 발전량 해석 보조 |

Quality feature가 예측 모델 입력으로 사용될 경우, 학습 시점에 알 수 없는 사후 품질 정보를 포함하지 않는다.

## 11. Feature naming 규칙

Feature name은 다음 구성요소를 사용한다.

```text
<scope>__<group_or_building>__<measurement_or_family>__<stat>__<window_or_resolution>
```

예시:

| Feature name | 의미 |
|---|---|
| `group__central_cooling__electricity_power__sum__15min` | 중앙 냉각기 15분 전력 합계 |
| `group__server_power__electricity_power__sum_primary__15min` | 서버 전원 redundant 제외 합계 |
| `pair__H2_Z64_H2_ZE64__electricity_power__abs_diff__15min` | redundancy pair 절대 차이 |
| `weather__station__temperature__mean__1h` | 기상 station 1시간 평균 |
| `building__H2__electricity_power__sum__15min` | H2 building 전력 소비 합계 |

Naming 규칙:

1. 구분자는 `__`를 사용한다.
2. Meter URN을 feature name에 넣을 때 `.`는 `_`로 치환한다.
3. Aggregate와 pair comparison feature를 같은 prefix로 섞지 않는다.
4. Resolution을 feature name 또는 feature metadata에 명시한다.
5. Feature 산출물에는 원 feature name과 사람이 읽는 설명을 함께 기록한다.

## 12. Wide format 전환 기준

Wide format은 모델 입력 직전에 생성한다.

전환 전 확인 항목:

1. `(ts, meter_urn, measurement, resolution_code)` 중복이 없어야 한다.
2. Feature별 단위가 확정되어야 한다.
3. Feature별 결측 처리 규칙이 확정되어야 한다.
4. Redundancy 처리 방식이 metadata에 기록되어야 한다.
5. Feature 생성에 사용한 meter set이 저장되어야 한다.
6. 학습 구간과 live replay 구간의 column set이 동일해야 한다.

Wide table의 index는 `ts`를 기본으로 한다. Multi-target 또는 group별 모델에서는 `target_scope`를 별도 column으로 둘 수 있다.

## 13. Live replay feature 기준

Live replay feature는 `docs/specs/프로젝트_개요.md`의 live replay 평가 원칙과 다음 tick 규칙을 따른다.

| 항목 | 기준 |
|---|---|
| 기본 tick | `15min` |
| 학습 구간 | split timestamp 이전 |
| replay 구간 | split timestamp 이후 |
| feature fit | 학습 구간만 사용 |
| feature transform | 현재 tick 이전 데이터만 사용 |
| prediction 생성 | 실측값 평가 전 |
| error 계산 | 실측값 도착 후 |

금지 항목:

1. Replay 전체 기간의 평균, 표준편차, 결측률을 학습 전처리 기준에 사용하지 않는다.
2. 미래 tick의 보간값을 현재 tick feature에 사용하지 않는다.
3. Replay 구간의 target 실측값을 같은 tick의 prediction feature로 사용하지 않는다.
4. 사후 anomaly label을 feature 입력으로 사용하지 않는다.

## 14. Feature 산출물 저장 기준

초기 산출물은 파일 기반으로 두고, DB 저장 table은 별도 승인 후 생성한다.

| 산출물 | 저장 후보 | 기준 |
|---|---|---|
| feature matrix | `outputs/tables/<analysis_slug>/` | 재생성 가능한 모델 입력 |
| feature metadata | `outputs/tables/<analysis_slug>/` | feature name, source, unit, meter set, window |
| feature quality summary | `outputs/tables/<analysis_slug>/` | 결측률, coverage, excluded row count |
| report | `reports/<analysis_slug>/report.md` | feature 설계와 결과 요약 |
| figure | `outputs/figures/<analysis_slug>/` | feature distribution, missingness, trend |

DB table 후보는 feature 저장 위치와 명명 규칙이 안정화된 뒤 별도 승인된 schema 계획에서 정의한다.

| `created_at` | 생성 시각 |

## 17. 검증 기준

Feature 생성 스크립트는 최소한 다음 검증을 통과해야 한다.

1. 입력 relation 또는 Parquet dataset이 `데이터_계약.md`의 저장소 경계를 따른다.
2. 입력 row grain이 `데이터_계약.md`와 일치한다.
3. 사용한 meter set이 ontology helper 결과와 일치한다.
4. 사용한 measurement가 measurement registry에 존재한다.
5. Aggregate feature에서 redundant endpoint를 중복 합산하지 않는다.
6. Production과 consumption을 같은 aggregate로 합산하지 않는다.
7. Weather meter를 energy aggregate에 포함하지 않는다.
8. Wide format column 수와 feature metadata row 수가 일치한다.
9. Train/live replay split 이후 미래 데이터가 현재 tick feature에 포함되지 않는다.
10. Feature 산출물에 source relation, resolution, period, meter set, redundancy policy가 기록된다.

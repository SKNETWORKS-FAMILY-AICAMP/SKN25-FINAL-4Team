# EMS 프로젝트 개요

**갱신일:** 2026-05-13  
**범위:** 프로젝트 목적, 기준 데이터, 분석 범위, 평가 원칙, 구현 경계.

---

## 1. 목적

EMS는 PostgreSQL/TimescaleDB `ems` schema를 기준 원천으로 사용하는 DB 중심 에너지 분석 프로젝트다. 분석 목적은 스마트 빌딩 및 산업시설의 전력, 열·냉방, 기상 계측 데이터를 활용해 설비 단위 검증, 이상 징후 탐지, 에너지 사용 예측, 보고 지표 산출을 수행하는 것이다.

분석 단위는 다음 조합으로 정의한다.

```text
(ts, meter_urn, measurement, resolution_code)
```

## 2. 기준 데이터

| 항목 | 기준 |
|---|---|
| 데이터셋 | 스마트 회사 건물의 EMS 최적화 및 machine learning용 실측 에너지 관리 데이터셋 |
| 논문 | Scientific Data 2025, DOI `10.1038/s41597-025-05186-3` |
| 데이터 저장소 | Dryad DOI `10.5061/dryad.73n5tb363` |
| 수집 시설 | 독일 Offenbach am Main 소재 Honda R&D Europe 시설 |
| 수집 기간 | 2018-01-01 00:00 GMT+1부터 2024-01-01 00:00 GMT+1까지 |
| 로컬 시간대 | Europe/Berlin |
| 계측 범위 | 전력, 열·냉방, 기상 |
| 계량기 수 | 81개 URN |
| 원천 파일 형식 | gzip CSV |

시설은 사무실, 워크숍, 서버룸, 차량 배출 실험실을 포함한 중규모 산업 시설이다. 주요 설비는 PV, gas-fired CHP, 중앙 water chiller, gas boiler, CHP 열 생산 계통, 현장 기상 관측소다.

---

## 3. 처리 계보

원천 데이터는 계량기 URN 단위 디렉터리와 측정 항목별 gzip CSV 파일로 구성된다. DB 적재 후 파일 단위 정보는 `ems.full_source_file`에서 관리한다.

| 단계 | 의미 | 분석 사용 기준 |
|---|---|---|
| `raw` | 원시 수집값 | 원인 추적, 보정 전 상태 확인 |
| `harmonized` | 명칭, 단위, 부호 규약 정합화 | 처리 계보 확인 |
| `corrected` | 이슈 보정과 시간 정렬 반영 | 보정 후 native 시계열 확인 |
| `corrected_resampled` | 1min, 15min, 1h 등간격 리샘플링 | 분석 기본 후보 |

## 4. 분석 도메인

| 도메인 | 분석 의미 | 대표 measurement |
|---|---|---|
| 전력 소비 | 외부 전력망 유입, 구역별 배전, 설비별 소비 | `P`, `W`, `I1`, `I2`, `I3`, `U1`, `U2`, `U3`, `PF` |
| 전력 생산 | CHP, PV 발전량 | `P`, `W`, `W_in`, `W_out` |
| 열 생산 | 총 열 생산, CHP 열 생산 | `P`, `W`, `Tvl`, `Trl`, `Tdiff`, `qv`, `V` |
| 냉방 | 중앙 냉각기 및 로컬 냉각 설비 | 전기 계측값, 열 계측값 |
| 기상 | 외기 조건과 일사량 | `Ta`, `Igc`, `Igm`, `Ua`, `Sc`, `Dc`, `Dp`, `H`, `rho` |

기상 measurement 식별자는 DB 적재명 기준으로 `Ah`, `Igc`, `Igm`, `Sc`, `Ta`, `Ua`, `rho`를 사용한다. `Pa`는 registry에는 유지하지만 source file metadata에서 확인되지 않았으므로 기본 분석 입력에서 제외한다.

---

## 5. 분석 요구사항

| 영역 | 요구사항 |
|---|---|
| 데이터 접근 | 기간, 계량기, measurement, 해상도 조건으로 `ems` schema를 조회한다. |
| 전처리 | timestamp 정렬, 결측, non-finite, 중복, 부호 규약, 누적값 차분 안정성을 검증한다. |
| 이상탐지 | 통계 기준, 계절 보정, 다변량 모델, 복원 기반 모델 후보를 비교한다. |
| 예측 | lag, rolling, 기상, calendar feature를 사용해 단기·중기 예측 baseline을 구성한다. |
| 보고 | 월간 에너지 요약, 이상탐지 요약, 예측 비교, 설비 진단, 데이터 품질 요약을 산출한다. |

구현 우선순위는 DB 조회와 데이터 계약 확정, 계량기 metadata 정규화, 전처리 및 품질 검증, baseline 이상탐지, aggregate 예측, 보고 지표 순서로 둔다.

## 6. Live replay 평가 원칙

EMS 시계열 평가는 시간 순서를 보존한다. 초기 평가는 앞 구간으로 전처리 규칙, 정상 baseline, 모델, threshold를 만들고 뒤 구간을 순차 도착 데이터로 처리하는 live replay 방식을 사용한다.

| 항목 | 기준 |
|---|---|
| 기본 tick | `15min` |
| 보조 해상도 | `1h` 보고 지표, `1min` event-level 분석 후보 |
| feature fit | 학습 구간만 사용 |
| feature transform | 현재 tick 이전 데이터만 사용 |
| prediction 생성 | 실측값 평가 전 |
| error 계산 | 실측값 도착 후 |

금지 항목은 replay 전체 기간 통계의 사전 사용, 미래 tick 보간값 사용, 같은 tick target 실측값의 prediction feature 사용, 사후 anomaly label의 feature 입력 사용이다.

---

## 7. 구현 경계

1. 데이터 원천은 PostgreSQL/TimescaleDB `ems` schema로 둔다.
2. 로컬 `data/` 디렉터리를 프로젝트 원천으로 사용하지 않는다.
3. 파일 기반 원본 구조는 DB 재적재와 데이터 계보 이해에만 사용한다.
4. 민감정보, 접속정보, 계정 정보는 문서에 기록하지 않는다.
5. DB write, destructive SQL, 대용량 적재는 명시적 승인 후 실행한다.
6. DB 재적재용 로더와 SQL은 보존용 archive에 둔다.
7. 사용자 인터페이스, 백엔드 API, 프론트엔드 구현은 별도 구현 단계에서 범위를 확정한다.

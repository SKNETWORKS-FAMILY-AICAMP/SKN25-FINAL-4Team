# 기획서 분석: 현재 프로젝트와의 갭 분석

**기획서**: `스마트 건물 에너지 데이터 분석 및 대화형 AI 플랫폼 기획서`
**분석 대상**: 현재 EMS 프로젝트의 DB, 노트북, 온톨로지, 논문, 스펙 문서

---

## 한줄 요약

이 기획서는 현재 프로젝트를 **"DB 중심 분석 유틸리티" → "대화형 AI 에이전트 플랫폼"으로 확장**하려는 비전을 담고 있다. 기존에 쌓아둔 인프라(TimescaleDB 스키마, 데이터 계약, 온톨로지)가 Phase 1의 상당 부분을 이미 커버하고 있어 출발 조건이 좋지만, 기획서와 현실 사이에 채워야 할 갭이 명확하게 존재한다.

---

## Phase별 갭 분석

### Phase 1: DB 스키마 설계

| 항목 | 기획서 요구사항 | 현재 상태 | 갭 |
|---|---|---|---|
| 시계열 테이블 | TimescaleDB 기반 시계열 저장 | ✅ `cr_measurement_15min`, `cr_measurement_1h` hypertable 구축 완료 | 없음 |
| 장비 메타데이터 | 장비별 분류, 그룹핑, 관계 정의 | ⚠️ `full_meter`에 `meter_urn`, `meter_group`만 존재. 설비 classification, domain, redundancy 관계는 **DB 미승격** | **`계량기_메타데이터.md`를 기반으로 장비 분류 테이블 DB 승격 필요** |
| Reduced 데이터 | 전기/난방/냉방/기상 4대 범주로 압축 합산 | ❌ DB에 reduced 계층 없음 | **논문 Table 8의 aggregated dataset 기준으로 뷰 또는 테이블 생성 필요** |
| 온톨로지 | 계량기 계층 구조 (Fig.1 트리) | ✅ `docs/ontology/ems.ttl`, `ems_protege.owl` 존재 | 온톨로지와 DB 메타데이터 연동 로직 필요 |

> [!IMPORTANT]
> 기획서에서 말하는 "Reduced 데이터"는 논문의 Table 8에 정의된 aggregated dataset이다. 현재 DB에는 개별 계량기 단위 데이터만 있으므로, 아래 URN 그룹 기준의 합산 뷰를 새로 만들어야 한다:
> - **전기 총소비**: V.Z81 + V.Z82 + H2.Z35/Z351 + H2.Z36/Z361
> - **PV 생산**: V.Z84 + H1.Z310 + H1.Z311 + H1.Z312
> - **CHP 전기**: H1.Z20
> - **냉각기 전기**: H1.Z16 + H1.Z11 + H1.Z12 + H1.Z24 + H1.Z25

### Phase 2: 분석 에이전트 (Text-to-SQL)

| 항목 | 기획서 요구사항 | 현재 상태 | 갭 |
|---|---|---|---|
| LLM 프레임워크 | 자연어 → SQL 변환 에이전트 | ⚠️ `requirements.txt`에 LangChain, LangGraph, OpenAI, Anthropic, Google GenAI 패키지 모두 포함 | **실제 에이전트 코드가 아직 없음** |
| DB 스키마 이해 | LLM이 테이블 구조를 참조 | ✅ `데이터베이스_구조.md`, `데이터_계약.md`에 상세 문서화 | 이 문서를 LLM 시스템 프롬프트에 주입하는 로직 필요 |
| 기본 EDA | Reduced 데이터 기반 트렌드 분석 | ⚠️ `01_eda.ipynb`가 H1.Z16 단일 계량기 대상으로 EDA 수행 중 | Reduced 전체 기준의 EDA로 확장 필요 |

> [!TIP]
> Text-to-SQL 에이전트 구축 시, 현재 `docs/specs/` 문서(DB 구조, 데이터 계약, 피처 명세, 계량기 메타데이터, 온톨로지 스키마)가 LLM의 컨텍스트로 직접 활용 가능하다. 이 문서들의 품질이 매우 높으므로 프롬프트 엔지니어링의 핵심 자산이 된다.

### Phase 3: 비용 최적화 (역률/무효전력)

| 항목 | 기획서 요구사항 | 현재 상태 | 갭 |
|---|---|---|---|
| 역률(PF) 분석 | 역률 저하 구간 식별, 과태료 위험 경고 | ⚠️ `01_eda.ipynb`에서 H1.Z16의 PF를 조회하고 상관분석 수행 중 | 전체 계량기 대상으로 확장 + 한국 전기요금 기준 역률 벌금 룰 적용 필요 |
| 무효전력(Q, WQ) | 지상/진상 부하 밸런스 분석 | ⚠️ 기획서에서 WQ_in/WQ_out 패턴 분석이 언급되었고, EDA에서 일부 조회 | 비용 최적화 로직 (진상 콘덴서 On/Off 제어 룰) 구현 필요 |
| PV 역송전 | 마이너스 역률 시 무효전력 반환 분석 | ⚠️ 기획서 2.2에서 "2019년 6월 PV 가동 후 WQ_out 증가" 언급 | PV 가동 전후를 구분하는 시계열 분할(Concept Drift 대응) 필요 |

> [!WARNING]
> 기획서는 "중소 제조업 대상"을 명시한다. Honda 시설 데이터는 독일 전력망 기준이므로, 한국 산업용 전기요금 체계(역률 90% 미만 시 기본요금 추가 등)에 맞는 **비용 산출 룰을 별도로 정의**해야 한다. 데이터의 물리적 패턴은 그대로 활용 가능하지만, 금액 계산 로직은 한국 기준으로 새로 만들어야 함.

### Phase 4: 이상 탐지 모델링

| 항목 | 기획서 요구사항 | 현재 상태 | 갭 |
|---|---|---|---|
| Isolation Forest | Raw 데이터 기반 이상 탐지 | ✅ `02_iforest.ipynb` 존재 | 세부 내용 확인 필요 (학습/평가 분리, labeled issues 활용 여부) |
| Labeled Issues 활용 | 논문 제공 정답 라벨로 지도학습 | ⚠️ 논문에서 142,207건의 Gap, 6,752건의 Zero measurement 등을 자동 라벨링했다고 명시 | **라벨 데이터를 DB에 적재하고 정답지로 활용하는 파이프라인 필요** |
| 실시간 모니터링 | 백그라운드 모니터링 + 즉각 경고 | ❌ 현재 배치 분석만 존재 | 스트리밍/스케줄링 인프라 필요 (기획서의 k3s 오케스트레이션과 연결) |

> [!IMPORTANT]
> 논문의 Technical Validation에서 확인된 이슈 통계:
> - **Gap(결측)**: 142,207건, 평균 3,283초(약 55분), 전체 시간의 3.12%
> - **Lasting leap(지속 도약)**: 1건
> - **Single leap(단발 도약)**: 3건
> - **Zero measurement(영점 측정)**: 6,752건
>
> 이 라벨들이 이상 탐지 모델의 Ground Truth가 된다.

## 현재 프로젝트의 숨은 자산 (기획서에서 직접 언급하지 않지만 활용 가능한 것)

| 자산 | 위치 | 활용 가치 |
|---|---|---|
| **온톨로지 (OWL/TTL)** | `docs/ontology/` | 계량기 계층 구조를 SPARQL로 질의 가능. AI 에이전트가 "이 냉각기의 상위 시스템은?" 같은 질문에 답할 수 있음 |
| **데이터 계약 문서** | `docs/specs/데이터_계약.md` | Text-to-SQL 에이전트의 시스템 프롬프트로 직접 주입하면 환각(Hallucination) 대폭 감소 |
| **피처 명세** | `docs/specs/피처_명세.md` | 예측/이상탐지 모델의 입력 변수 설계가 이미 문서화됨. 모델링 단계에서 바로 참조 가능 |
| **Live Replay 평가 원칙** | `docs/specs/프로젝트_개요.md` §6 | 시계열 모델 평가 시 미래 데이터 누수(data leakage) 방지 규칙이 엄격하게 정의됨 |
| **MLflow** | `requirements.txt` | 실험 추적, 모델 버저닝에 활용 가능 |
| **Docker Compose** | `docker-compose.yml` | 로컬 개발환경 컨테이너화 기반 존재 |

## 권장 우선순위

기획서의 5단계 로드맵과 현재 갭을 종합하면, 다음 순서로 진행하는 것이 효율적이다:

1. **Phase 1 마무리**: `계량기_메타데이터.md` → DB 테이블 승격 + Reduced 합산 뷰 생성
2. **Phase 2 착수**: LangChain/LangGraph 기반 Text-to-SQL 에이전트 프로토타입 (DB 스키마 문서를 컨텍스트로 활용)
3. **Phase 4 병행**: `02_iforest.ipynb` 고도화 + 논문 라벨 데이터 활용
4. **Phase 3**: 역률/무효전력 비용 최적화 룰 엔진 (한국 기준 적용)
5. **Phase 5**: 자동 리포팅 (앞 단계의 산출물이 확보된 후)

> [!CAUTION]
> 기획서에서 언급한 **"On-Premise 하이브리드 구조(NAS + k3s + 로컬 LLM)"**은 인프라 설계에 해당하며, 현재 프로젝트 범위(`구현 경계` §7)에서 "사용자 인터페이스, 백엔드 API, 프론트엔드 구현은 별도 구현 단계에서 범위를 확정"이라고 명시되어 있다. 따라서 먼저 **분석 로직과 에이전트 코어를 완성**한 뒤, 배포 인프라는 별도 단계에서 결정하는 것이 맞다.

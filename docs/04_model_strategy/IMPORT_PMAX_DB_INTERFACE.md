# Import P-Max 예측 모델 DB 연동 명세

## 1. 목적

본 모델은 전기 계량기의 향후 네 개 15분 구간별 수입 전력 최댓값(`P_max`)을 예측한다.

- 입력 주기: 15분
- 입력 구간: 최근 24시간, 96개 시점
- 출력: 요청 시각 이후 네 개 15분 구간
- 모델: 4개 회귀 모델의 가중 앙상블
- 구성 모델: LightGBM 2개, XGBoost 1개, CatBoost 1개
- 현재 운영 모델: 22개 feature, 제한적 결측 보정 정책 적용 모델

현재 모델은 열량계를 대상으로 하지 않는다.

---

## 2. 대상 계량기

| 논리 계량기 | DB 원천 계량기 | 비고 |
|---|---|---|
| `V.Z81` | `V.Z81` | 단일 계량기 |
| `V.Z82` | `V.Z82` | 단일 계량기 |
| `H2.Z35x` | `H2.Z35`, `H2.Z351` | 시기별 연결 계량기 |
| `H2.Z36x` | `H2.Z36`, `H2.Z361` | 시기별 연결 계량기 |

`H2.Z35x`, `H2.Z36x`는 계량기 교체 전·후 데이터를 하나의 논리 계량기로 관리한다. 두 원천 계량기의 값을 합산하거나 하나의 입력 window에서 혼합하지 않으며, 단일 원천 계량기의 연속된 24시간 구간만 사용한다.

---

## 3. 입력 테이블

기본 조회 테이블:

```text
mart.peak_feature_15min
```

필요한 컬럼:

| 컬럼 | 설명 |
|---|---|
| `window_ts` | 15분 bucket 시작시각 |
| `meter_urn` | 계량기 식별자 |
| `measurement` | 측정 항목 |
| `mean_value` | 해당 15분 구간 평균값 |
| `max_value` | 해당 15분 구간 최댓값 |
| `std_value` | 해당 15분 구간 표준편차 |
| `coverage_ratio` | 원천 데이터 커버리지 |
| `created_at` | 집계 데이터 생성 시각 |
| `run_id` | 동일 구간 재생성 시 최신 실행 식별자 |

동일한 `(window_ts, meter_urn, measurement)`가 여러 건이면 `created_at DESC, run_id DESC` 기준 최신 행을 사용한다.

### `window_ts` 정의

DB 적재 기준은 bucket 시작시각이다.

```text
window_ts = 23:15
집계 구간 = [23:15:00, 23:30:00)
```

따라서 `23:45`에 예측을 요청할 경우 가장 최근에 완료된 입력 bucket은 다음과 같다.

```text
input_end_ts = 23:30
입력값의 실제 집계 구간 = [23:30, 23:45)
```

`window_ts=23:45` 행은 `[23:45, 00:00)` 구간을 의미하므로 `23:45` 요청의 입력으로 사용하지 않는다.

## 4. 필요한 측정 항목

### 전기 계량기

| measurement | 사용하는 집계값 | 모델 입력명 |
|---|---|---|
| `P` | `mean_value` | `P_mean` |
| `P` | `max_value` | `P_max` |
| `P` | `std_value` | `P_std` |
| `U1` | `mean_value` | `U1_mean` |
| `PF` | `mean_value` | `PF_mean` |

예측 대상은 `P` 원천값 자체가 아니라 각 15분 구간의 `P.max_value`, 즉 `P_max`이다. 음수 `P_mean`, `P_max`는 0으로 보정한다.

## 5. 시간 및 데이터 품질 조건

- 모든 `window_ts`는 UTC 기준으로 처리한다.
- 데이터는 정확히 15분 간격이어야 한다.
- 동일 키 중복은 허용되지만 최신 행을 판별할 수 있어야 한다.
- `P`, `U1`, `PF`가 같은 `window_ts` 기준으로 조회 가능해야 한다.
- 과거 입력 구간 내부 결측은 앞뒤 관측값이 있으면 연속 최대 60분까지 선형보간한다.
- 24시간 입력 window 안에서는 하나의 내부 결측 구간만 허용한다.
- 결측 보정이 한 행이라도 적용된 예측은 품질 상태를 `degraded`로 표시한다.
- 요청 직전 최신 입력 bucket 한 개가 결측이면 직전 관측값으로 대체한다.
- 요청 직전 30분 이상이 연속 결측이면 추론을 실패 처리한다.
- 내부 보간과 최신값 대체를 합친 총 대체 행은 24시간 window에서 최대 4행으로 제한한다.
- 학습·검증·테스트 target인 `P_max`는 보간값을 정답으로 사용하지 않는다.
- 결측이 없으면 값 변경 없이 기존 전처리와 동일하게 진행한다.

결측은 다음 두 경우를 포함한다.

- 해당 `window_ts` 행은 있으나 필수 측정값 중 일부가 NaN인 경우
- 해당 `window_ts` 행 자체가 한 개 누락된 경우

전날 같은 시각 값으로 대체하는 방식은 요청 직전 결측 실험에서 성능 저하가 커 사용하지 않는다. DB에서 결측 구간을 임의로 채우지 않고 원본 결측 상태로 제공해야 모델이 정책에 따라 처리할 수 있다.

적용하는 기본 물리 규칙:

| 항목 | 처리 |
|---|---|
| `P_mean < 0` | 0으로 보정 |
| `P_max < 0` | 0으로 보정 |
| `U1_mean <= 0` 또는 `U1_mean > 1000` | 결측 처리 |
| `abs(PF_mean) > 1.5` | 결측 처리 |

## 6. 모델 내부 생성 피처

DB에서 별도로 제공할 필요가 없다.

### 시간 피처

- `hour_sin`, `hour_cos`
- `dayofweek_sin`

### Lag 및 변화량 피처

- `P_max_lag_1`
- `P_max_lag_96`: 24시간 전
- `P_max_lag_192`: 48시간 전
- `P_max_diff_1`, `P_max_diff_4`
- `P_mean_diff_1`
- `U1_mean_diff_1`
- `PF_mean_diff_1`

### Rolling 피처

- 최근 1시간 `P_max` 평균, 최댓값, 표준편차
- 최근 3시간 `P_max` 평균, 최댓값
- 최근 6시간 `P_max` 평균

시점당 총 22개 피처를 사용하며, 96개 시점을 펼쳐 총 2,112개 입력값으로 모델에 전달한다.

이론상 최소 요구 구간:

```text
48시간 lag 생성 + 24시간 모델 입력 = 최소 72시간
```

운영 조회 조건:

- 기본 조회 범위: 최근 14일
- 실제 모델 입력: 조회 데이터 중 가장 최근의 유효한 연속 24시간

결측이나 누락 구간이 있을 수 있으므로 운영에서는 기본 14일 조회를 권장한다.

## 8. 모델 출력

요청 시각 기준 다음 네 개 15분 bucket의 `P_max` 예측값을 각각 반환한다.

예를 들어 `base_ts=23:45`인 경우:

| horizon | 예측 구간 | 저장 `target_ts` |
|---:|---|---|
| 15분 | `[23:45, 00:00)` | `00:00` |
| 30분 | `[00:00, 00:15)` | `00:15` |
| 45분 | `[00:15, 00:30)` | `00:30` |
| 60분 | `[00:30, 00:45)` | `00:45` |

`target_ts`는 예측 bucket의 **종료시각**이다. 예측 구간 시작시각은 `target_ts - 15분`으로 계산할 수 있다.

현재 JSON에는 네 예측 중 가장 큰 값을 `next_60min_peak`로 추가 제공하지만 이는 부가 요약 정보다. CSV 출력은 DB 저장 구조와 동일한 네 행으로 생성된다. 예측 결과를 DB에 직접 INSERT하는 로직은 아직 구현되지 않았다.

4개 논리 계량기를 일괄 추론하면 계량기당 네 행씩 총 16행의 실행별 CSV를 생성한다. 동시에 `outputs/import_pmax/import_pmax_forecast_history.csv`에 동일한 16행을 누적 UPSERT한다. 새 `base_ts`의 실행은 16행을 추가하고, 동일 `base_ts` 재실행은 권장 유일 키 `(logical_meter, base_ts, target_ts)`가 같은 기존 16행을 갱신한다. 이 누적 CSV는 DB 연동 전 단일 예측 테이블 적재 동작을 검증하기 위한 파일이다.

현재 일괄 추론은 한 계량기라도 실패하면 전체 실행을 실패 처리하고 CSV·JSON을 저장하지 않는다.

## 9. 예측 결과 저장 테이블 권장안

권장 테이블명:

```text
mart.import_pmax_forecast_15min
```

권장 컬럼:

| 컬럼 | 권장 타입 | 설명 |
|---|---|---|
| `logical_meter` | VARCHAR | 논리 계량기 |
| `source_meter_urn` | VARCHAR | 실제 입력에 사용된 원천 계량기 |
| `base_ts` | TIMESTAMPTZ | 예측 요청 및 기준 시각 |
| `input_end_ts` | TIMESTAMPTZ | 마지막 입력 bucket의 시작시각, 정상 상태에서는 `base_ts - 15분` |
| `target_ts` | TIMESTAMPTZ | 예측 대상 15분 bucket의 종료시각 |
| `horizon_minutes` | SMALLINT | 15, 30, 45, 60 |
| `predicted_p_max` | DOUBLE PRECISION | 최종 앙상블 예측값, 음수는 0으로 보정 |
| `created_at` | TIMESTAMPTZ | 예측 저장 시각 |

권장 유일 키:

```text
(logical_meter, base_ts, target_ts)
```

동일 기준 시각에 재실행하면 같은 예측 행을 갱신하는 방식이 단순하다. 모델 교체 이력을 별도로 관리해야 하는 시점에는 모델 배포 이력 테이블을 추가하거나 `model_version` 컬럼을 확장할 수 있다.

DB 연동 전에는 누적 CSV가 같은 키 정책을 구현한다. 실제 DB 연동 시에는 누적 CSV 자체를 운영 저장소로 사용하지 않고 동일 키의 `INSERT ... ON CONFLICT ... DO UPDATE` 또는 동등한 UPSERT로 교체한다.

현재 최소 CSV 스키마에는 결측 보정 여부가 포함되지 않는다. `data_quality.status`, 보간 행 수와 같은 정보는 JSON에만 포함된다. DB에서도 품질 상태를 관리해야 한다면 별도 실행 로그 테이블에 저장하거나 예측 테이블에 품질 컬럼을 추가해야 한다.

예시:

```text
logical_meter   = V.Z81
source_meter_urn = V.Z81
base_ts          = 2026-06-06 23:45:00+00
input_end_ts     = 2026-06-06 23:30:00+00
target_ts        = 2026-06-07 00:00:00+00
horizon_minutes  = 15
predicted_p_max  = 12345.67
created_at       = 2026-06-06 23:45:05+00
```

## 10. 실측 결합 및 사후 평가 선택안

실측값이 확정된 후 별도 평가 테이블 또는 동일 테이블 확장으로 다음 정보를 관리할 수 있다.

예측 테이블의 `target_ts`는 bucket 종료시각이고 원천 실측 테이블의 `window_ts`는 bucket 시작시각이므로 다음 기준으로 결합해야 한다.

```text
actual.window_ts = forecast.target_ts - INTERVAL '15 minutes'
```

예:

```text
예측 target_ts = 00:00
실측 window_ts = 23:45
공통 구간      = [23:45, 00:00)
```

| 컬럼 | 설명 |
|---|---|
| `actual_p_max` | 예측 대상 15분 구간의 실제 `P_max` |
| `absolute_error` | `abs(actual_p_max - predicted_p_max)` |
| `squared_error` | `(actual_p_max - predicted_p_max)^2` |
| `evaluated_at` | 실측 결합 시각 |

현재 모델 목적은 순수 피크 전력 예측이다. 경고·이상탐지 threshold는 현재 모델 범위에 포함되지 않으며, 필요 시 별도 정책 계층에서 구현한다.

## 11. 운영 처리 흐름

1. `mart.peak_feature_15min`에서 최근 데이터를 조회한다.
2. 동일 키의 최신 중복 행을 선택한다.
3. 요청 시각보다 15분 전의 완료된 bucket을 마지막 입력으로 확정한다.
4. 내부 결측은 연속 최대 60분까지 선형보간한다.
5. 최신 15분 bucket만 결측이면 직전값으로 대체하고 `degraded`로 표시한다.
6. 입력 window의 결측 구간 수와 총 대체 행 제한을 검증한다.
7. 시간, lag, rolling, diff feature를 생성한다.
8. 최근 24시간의 96행 입력 window를 구성한다.
9. LightGBM 2개, XGBoost, CatBoost 모델을 실행하고 앙상블 예측값을 계산한다.
10. 요청 시각 이후 네 개 15분 구간별 최대 P 예측값을 생성한다.
11. 4개 논리 계량기에서 총 16개 예측 행을 생성한다.
12. API 응답용 통합 JSON과 실행별 16행 CSV를 생성한다.
13. DB 연동 전 검증용 누적 CSV에 유일 키 기준으로 UPSERT한다.

---

## 12. DB 관리자 확인 및 협의사항

현재 확인된 집계 기준:

- `window_ts`는 15분 bucket 시작시각
- 예: `23:15`는 `[23:15, 23:30)` 구간
- `P.max_value`는 해당 15분 구간 내 최대 P

운영 연동 시 필요한 사항:

1. `P`, `U1`, `PF` 집계가 동일한 `window_ts` 기준으로 완료되는 시점
2. 15분 bucket 적재 완료 여부를 판별할 수 있는 기준
3. 누락 bucket을 행 누락으로 제공하는지, 행은 생성하고 값만 NaN으로 제공하는지
4. 예측 결과 테이블의 생성 및 UPSERT 담당 주체
5. 운영 스케줄러가 매 15분 경계 이후 몇 분에 추론을 실행할지

## 13. 현재 검증 상태

- 22개 feature 모델을 4개 논리 계량기 전체에 대해 재학습 완료
- 내부 연속 최대 60분 선형보간 전처리를 학습과 추론 코드에 동일하게 적용
- 요청 직전 15분 결측의 직전값 대체 및 `degraded` 품질 표시를 추론에 적용
- 요청 직전 30분 이상 결측은 추론 실패 처리
- 결측 정책 변경 후 정상 입력 재현 검증과 인위적 결측 경계 검증을 완료
- 학습 원본에는 실제 내부 결측이 없어 기존 artifact의 정상 입력 예측값은 변경되지 않음
- 결측이 없는 기존 데이터에서는 보간 적용 전 모델과 예측값이 동일함을 확인
- 검증 기간: `2023-06-30 22:00 UTC`부터 `2023-12-31 22:00 UTC`
- 총 추론 요청: 70,660건
- 생성된 예측 결과: 282,640행
- 추론 실패: 0건
- 필수 컬럼의 null, 결과 중복, 음수 최종 예측: 0건
- 최종 운영 artifact로 4개 계량기 일괄 추론 검증 완료
- 일괄 추론 결과: 4개 계량기, 16행, null 0건, 중복 0건

현재 코드는 DB 조회와 CSV·JSON 출력까지 구현되어 있다. 운영 DB에 직접 INSERT 또는 UPSERT하는 단계는 DB 테이블과 실행 주체를 협의한 후 연결해야 한다.

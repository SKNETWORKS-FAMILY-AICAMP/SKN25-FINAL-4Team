Route1 / Route2 Label Guide

LangGraph Service Runtime Flow에서 Stage1(Route1)과 Stage2(Route2)가 어떤 질문을 어떤 경로로 보내는지 정리했습니다. 각 토글은 label별 설명과 실제 300-row router dataset에 가까운 예시 질문을 포함합니다.

Route1 · request type labels

query

분석·조회·설명형 질문입니다. 실제 운영 데이터를 읽어 이상 원인, 설비 상태, KPI, 예측, 계량기 의미를 답해야 하며 write나 승인 동작은 수행하지 않습니다. Stage2에서 anomaly/cms/report/forecast/domain_qa 중 하나로 이어집니다.

  1. 2023년 가을 CHP 관련 계량기에서 발생한 이슈는 몇 건이고, 분포는 어떻게 돼?
  2. 보일러 설비 상태가 어떤지 알려줘.
  3. 지난 24시간 운영 보고서 핵심 내용을 요약해줘.

action_request

사용자가 점검·정비·티켓 생성·담당자 배정처럼 운영 action을 요청하는 label입니다. 즉시 실행보다 작업 항목, 우선순위, 담당자, 안전 조건을 확인하고 CMS/작업지시 경로로 보내는 것이 핵심입니다.

  1. 3호 압축기 점검 작업을 등록해줘.
  2. B동 알람 확인 작업을 담당자에게 배정해줘.
  3. C동 점검 티켓을 생성해줘.

approval_required

삭제, 초기화, 강제 제어, 전체 승인처럼 위험하거나 권한 확인이 필요한 요청입니다. 모델은 실행했다고 말하지 않고 승인권자·영향 범위·rollback 가능성·안전 조건을 확인한 뒤 approval gate에 머물러야 합니다.

  1. 운영 테이블 데이터를 삭제해줘.
  2. CHP 설비 제어값을 강제로 변경해줘.
  3. 모든 알람을 승인 처리해줘.

off_topic

EMS, 에너지, 설비, 이상탐지, 운영 보고와 무관한 질문입니다. 주식·음식·스포츠·연예·날씨·의료 등 일반 주제는 서비스 범위를 벗어난다고 안내하고, 공장 EMS 관련 질문으로 재요청하도록 유도합니다.

  1. 오늘 점심 뭐 먹을까?
  2. 주식 종목 추천해줘.
  3. 어제 축구 경기 결과 알려줘.

multi_intent

분석, 보고서, 예측, 작업 등록처럼 여러 의도가 한 문장에 결합된 label입니다. 하나의 route로 억지 분류하지 않고 의도별로 분리하거나 우선순위를 물어보는 clarification gate로 보내는 것이 안전합니다.

  1. 2023년 11월 A동 이상 경보를 분석하고 보고서로 요약한 뒤 담당자에게 점검 작업도 등록해줘.
  2. 최근 2주 C동 알람 추이를 분석하고 다음 주 사용량도 예측해서 경영진 보고서로 만들어줘.
  3. H2.Z35x 의미를 설명하고, 이상 경보가 있으면 원인 분석과 작업 배정까지 해줘.
Route2 · service agent labels

anomaly

이상탐지 결과·경보·스파이크·잔차·원인·심각도 등 anomaly mart 근거를 조회하는 label입니다. 설비나 계량기에서 언제, 어떤 유형의 이상이 몇 건 발생했는지와 분포/원인을 설명합니다.

  1. 2023년 가을 PV 발전 전력 계량기에서 발생한 이슈는 몇 건이고, 분포는 어떻게 돼?
  2. PowerSpike 이상 후보는 몇 건 발생했나요?
  3. 냉방 장치 관련 계량기 이슈 분포를 알려줘.

cms

설비 상태, 정비 필요성, 작업지시, 점검 우선순위처럼 운영 관리/CMS 관점의 질문입니다. ops.work_order, 설비 상태, 작업 이력과 연결되며 action_request/approval_required도 최종적으로 이 경로에서 다룹니다.

  1. 보일러 설비 상태가 어떤지 알려줘.
  2. 3호 압축기 점검 우선순위가 어떤지 알려줘.
  3. 태양광 인버터 유지보수 리스크가 어떤지 알려줘.

report

월간·주간·일간 보고서, KPI 요약, 사용량, 비용, 자급률, 계통 의존도처럼 집계·요약된 운영 성과를 묻는 label입니다. ops.monthly_report 등 ops report schema/table을 중심으로 presentation-ready 답변을 만듭니다.

  1. 지난 24시간 운영 보고서 핵심 내용을 요약해줘.
  2. 최근 7일 에너지 사용 리포트 핵심 내용을 요약해줘.
  3. 2023년 11월 KPI 요약 핵심 내용을 요약해줘.

forecast

내일, 다음 달, 앞으로, 추세, 늘어날지/줄어들지 같은 미래 시점 예측 질문입니다. mart forecast schema/table과 reference time-series를 사용해 예상 방향, 불확실성, 확인해야 할 입력 조건을 함께 설명합니다.

  1. 다음 달 태양광 구역 전력 소비가 늘어날지 예측해줘.
  2. CHP2 라인 자급률이 늘어날지 예측해줘.
  3. 다음 달 태양광 구역 COP가 늘어날지 예측해줘.

domain_qa

계량기 의미, 설비/측정값 해석, 도메인 용어 설명처럼 도메인 지식 답변을 담당합니다. 기존 평가 label의 rag를 서비스 문서에서는 domain_qa로 표기하며, ontology와 ops.energy_doc, reference 근거를 사용합니다.

  1. H2.Z35x는 무엇을 측정하는 계량기야?
  2. V.Z82는 무엇을 측정하는 계량기야?
  3. P1.K03 계량기 값은 어떤 의미야?
Router Prompt 구성 · approval_required 강화 v2

우선순위

Route1은 multi_intent → approval_required → off_topic → action_request → query 순서로 판단하도록 강화했습니다. 특히 action_request를 선택하기 전에 반드시 위험/권한 side-effect 점검을 먼저 수행하게 했습니다.

  1. 복합 의도면 먼저 multi_intent
  2. 삭제·승인·강제제어·설정변경·재시작이면 approval_required
  3. 안전한 작업 등록/초안/담당자 배정만 action_request

approval_required hard rule

approval_required는 작업 요청의 하위 유형이 아니라 위험/권한 gate입니다. 시스템 상태 변경, 데이터 삭제/초기화, 승인 처리, 강제 제어, 임계값/설정 변경, 배포/반영, 서비스 시작·중지·재시작, 운영 DB write, 안전/비용 영향 가능성이 있으면 action_request가 아니라 반드시 approval_required로 선택하게 했습니다.

  1. 운영 테이블 데이터를 삭제해줘 → approval_required
  2. CHP 설비 제어값을 강제로 변경해줘 → approval_required
  3. 모든 알람을 승인 처리해줘 → approval_required

action_request 제한

action_request는 low-risk work planning에만 쓰도록 제한했습니다. 점검 티켓 생성, 작업 초안 작성, 담당자 배정, 점검 예약, 작업지시 준비처럼 파괴적/제어/승인/설정 변경 side effect가 없는 경우만 허용합니다.

  1. 3호 압축기 점검 작업을 등록해줘 → action_request
  2. C동 점검 티켓 초안을 만들어줘 → action_request
  3. 담당자 배정안을 작성해줘 → action_request

Negative rule

모델이 action_request로 흡수하던 문제를 줄이기 위해 명시적인 금지 규칙을 추가했습니다. 삭제/초기화/승인/제어/설정/배포/재시작/즉시 실행 요청은 절대 action_request로 분류하지 말고, action_request와 approval_required 사이에서 애매하면 approval_required를 선택하도록 했습니다.

  1. “처리해줘”, “실행해줘”, “적용해줘”가 포함돼도 위험 side effect가 있으면 approval_required
  2. read-only 설명 요청이면 query 유지
  3. 단순 작업 등록이면 action_request 유지

Final Acc

Router의 최종 action이 정답과 일치한 비율입니다. Stage1에서 질문이 일반 질의인지, 작업 요청인지, 승인 필요 요청인지, 범위 밖 질문인지 먼저 판단하고, Stage2에서 anomaly/cms/report/forecast/rag 중 어느 업무 agent로 보낼지 결정한 뒤 만들어지는 최종 라벨을 평가합니다. 예를 들어 “지난달 C동 PowerSpike 이상 후보는 몇 건 발생했나요?”는 설비 이상탐지 결과 조회이므로 정답 최종 action은 route:anomaly입니다. 모델이 route1=query, route2=anomaly, final_action=route:anomaly를 정확히 내면 정답 1건으로 계산됩니다. 반대로 route2를 report로 보내거나 JSON 계약을 지키지 못해 fallback이 나면 오답입니다. 그래서 Final Acc는 운영 라우터가 실제 사용자 질문을 올바른 처리 경로로 보내는 종합 정확도에 가장 가깝습니다.

correct final_action / total router rows

multi_intent F1

복합 의도 질문을 multi_intent 또는 clarification gate로 잡아내는 성능입니다. 예를 들어 “이상 경보를 분석하고 보고서로 요약한 뒤 정비팀 작업으로 등록해줘”는 anomaly 분석, report 생성, CMS 작업 등록이 한 문장에 섞인 요청입니다. 이런 질문을 무리하게 anomaly나 report 하나로 보내면 이후 단계에서 사용자가 기대하지 않은 자동 작업이 실행될 수 있습니다. 따라서 모델은 “어떤 작업을 먼저 수행할까요?”처럼 분리 질문이 필요한 multi_intent로 판단해야 합니다. F1은 precision과 recall의 균형이므로, multi_intent라고 예측한 것이 실제로 복합 의도였는지와 실제 복합 의도 질문을 놓치지 않았는지를 동시에 반영합니다. 값이 높을수록 애매한 복합 요청을 안전하게 게이트 처리한다고 해석할 수 있습니다.

2 × precision × recall / (precision + recall)

Numeric F1

QA 답변에서 숫자, 건수, 비율, 분포값 같은 정량 정보를 얼마나 정확히 회수했는지 보는 지표입니다. 예를 들어 “2023년 가을 CHP 관련 계량기에서 발생한 이슈는 몇 건이고, 분포는 어떻게 돼?”라는 질문의 기준 답변에 경보 단계 1440건, 경보 이벤트 898건, 고부하 684건, 저부하 756건이 들어 있다면, 모델 답변도 이 숫자들을 정확히 포함해야 높은 점수를 받습니다. 문장이 자연스럽고 설명이 길어도 핵심 숫자를 틀리거나 일부를 빠뜨리면 Numeric F1은 낮아집니다. 반대로 표현이 조금 투박해도 필요한 숫자와 분포를 정확히 회수하면 이 지표는 높게 나옵니다. 따라서 Numeric F1은 발표용 문장 품질보다 공장 EMS 챗봇이 실제 계량/경보 수치를 틀리지 않고 답하는지를 확인하는 지표입니다.

numeric precision/recall 기반 F1

BERTScore F1

생성 답변과 기준 답변의 의미적 유사도를 multilingual BERT embedding으로 비교한 F1입니다. 예를 들어 “2023년 가을 냉방 장치 관련 계량기에서 발생한 이슈는 몇 건이고, 분포는 어떻게 돼?”라는 질문에 대해 기준 답변은 냉방 장치 계량기 수, 경보 단계 수, 경보 이벤트 수, 원인 분포, 방향 분포를 포함합니다. 모델이 숫자를 완전히 같은 순서로 쓰지 않더라도 “냉방 장치 관련 계량기에서 저부하 경보가 더 많고, 알려진 계량기 이슈도 포함된다”처럼 의미적으로 기준 답변과 가까우면 BERTScore가 높아질 수 있습니다. 다만 빈 답변, 평가불가 답변, hidden reasoning/thinking text는 답변 품질로 인정하지 않고 evaluated_count와 unavailable_count로 분리합니다. 즉, BERTScore F1은 문장 의미 유사도를 보되, 실제 사용자에게 노출 가능한 답변만 평가 대상으로 삼는 지표입니다.

semantic similarity F1 over eligible answers

Fallback

모델이 평가 가능한 출력을 만들지 못한 건수입니다. Router 평가에서는 단순히 “이 질문은 이상탐지로 보입니다” 같은 자연어 설명이 아니라 {"route1":"query","route2":"anomaly","final_action":"route:anomaly"}처럼 허용된 key/value JSON을 내야 합니다. 모델이 JSON을 깨뜨리거나, 허용되지 않은 라벨을 쓰거나, content가 비거나, reasoning만 출력하거나, API/OOM/timeout이 발생하면 fallback으로 집계됩니다. 중요한 점은 fallback row를 rule-router 결과로 보정해서 모델 정답처럼 계산하지 않는다는 것입니다. fallback은 운영 환경에서 사용자가 질문했을 때 모델 출력 계약이 깨졌다는 뜻이므로, fallback이 많으면 accuracy가 어느 정도 높아 보여도 실제 라우터 후보로는 위험합니다. 특히 300건 전부 fallback인 모델은 판단 능력보다 출력 계약 자체를 만족하지 못한 것으로 해석해야 합니다.

Route2 Acc

Stage1에서 정상 query로 통과한 질문이 어떤 업무 agent로 가야 하는지 맞힌 비율입니다. 예를 들어 “다음 주 전력 사용량을 예측해줘”는 예측 업무이므로 route2=forecast가 맞고, “V.ZE84 계량기가 무슨 계량기야?”는 지식 조회이므로 route2=rag가 맞습니다. “지난달 C동 PowerSpike 이상 후보는 몇 건 발생했나요?”는 anomaly로 보내야 합니다. Route2 Acc는 이런 업무 분기만 따로 떼어 평가하므로, Stage1 전체 안전 게이트와는 다른 정보를 줍니다. 즉 Final Acc가 최종 운영 action의 종합 점수라면, Route2 Acc는 query로 들어온 질문이 anomaly/cms/report/forecast/rag 중 어느 전문 agent로 가야 하는지를 모델이 얼마나 잘 구분하는지 보여줍니다. 현재 LangGraph 그림의 box 이름이 아니라 Router 평가 표의 컬럼입니다.

## 3. 프로젝트 필요성

### 슬라이드 역할

제조업 에너지 관리의 정책적·운영적 필요성을 먼저 제시하고, EMS 데이터를 FEMS 분석과 AI 기반 운영 지원으로 확장해야 하는 이유를 설명합니다.

### 디자인 메모

- 핵심 이미지: 외부 압력과 내부 데이터 활용 간의 연결 구조. 별도 파일 없이 PPT 내부 도식으로 작성.
- 권장 구조: 좌측에는 `CBAM / K-ETS / 탄소중립 / 에너지 비용` 같은 외부 압력, 우측에는 `EMS 데이터 → 예측·이상탐지·피크관리·LLM 운영지원` 흐름.
- 시각 요소: 압력 요인 4개 카드 + EMS 데이터 활용 파이프라인.
- 핵심 강조: 이미 쌓이는 고해상도 EMS 데이터를 운영 판단으로 연결하는 것이 문제.
- 피해야 할 것: “월 단위 사용량만 본다”처럼 근거가 부족한 표현, CBAM을 제품별 내재배출량 산정 프로젝트처럼 과장하는 표현.

### 발표 대본 초안

제조업 현장은 에너지 비용 상승, 탄소중립 정책, K-ETS 고도화, EU CBAM 본격 적용과 같은 외부 압력을 동시에 받고 있습니다. 이에 따라 공장 단위의 전력 사용, 설비 운전, 피크 수요, 탄소 배출 영향을 더 정교하게 관리할 필요성이 커지고 있습니다.

많은 제조 현장에는 이미 EMS를 통해 1분·15분·1시간 단위의 고해상도 계측 데이터가 축적되고 있습니다. 전력 소비, 냉난방 설비, PV·CHP 발전, 기상 조건, 계량기별 부하 데이터가 존재하지만, 데이터가 존재하는 것만으로 운영 판단이 자동화되지는 않습니다.

피크 위험, 설비 이상 후보, 에너지 비효율, 발전 설비의 상쇄 효과는 여러 계측값과 시간 흐름을 함께 분석해야 드러납니다. 따라서 EMS 데이터는 단순히 저장하고 조회하는 수준에서 끝나서는 안 됩니다. 예측, 이상탐지, 설비 진단, 운영 의사결정 지원으로 이어지는 활용 체계가 필요합니다.

본 프로젝트는 공개된 독일 Honda R&D Europe EMS 데이터를 실증용 proxy로 사용해, 한국 제조업 현장에 적용 가능한 FEMS 분석 절차를 검증합니다. 최종 목표는 기존 EMS 데이터를 예측 모델, 이상탐지, 피크 관리, LLM 기반 질의·요약 기능과 연결하여 스마트 에너지 관리 시스템의 가능성을 확인하는 것입니다.

### 슬라이드 본문 후보

- 제조업은 에너지 비용, 탄소중립, K-ETS, CBAM 대응 압력을 동시에 받고 있음
- EMS에는 이미 고해상도 계측 데이터가 축적되지만, 데이터 존재만으로 운영 판단이 자동화되지는 않음
- 피크 위험, 설비 이상, 에너지 비효율은 시계열·설비 관계·외부 조건을 함께 분석해야 확인 가능
- 본 프로젝트는 EMS 데이터를 예측·이상탐지·FEMS 인사이트·LLM 기반 운영 지원으로 연결하는 절차를 검증

## 4. 프로젝트 개요

### 슬라이드 역할

프로젝트가 검증하려는 FEMS 데이터 인사이트 서비스의 범위와 분석 흐름을 한 장으로 정의합니다.

### 디자인 메모

- 핵심 이미지: `EMS 데이터 → 분석 엔진 → FEMS/LLM 운영지원` 3단 구조. 별도 파일 없이 PPT 내부 도식으로 작성.
- 시각 요소: 입력 데이터, 분석 기능, 사용자/운영자 결과를 구분한 블록 다이어그램.
- 핵심 강조: 독일 EMS 데이터는 실증용 proxy이고, 적용 목표는 한국 제조업 스마트 에너지 관리.
- 비즈니스 방향: 피크 위험 예측, 비용 리스크 추정, 계량기 품질 검증, 설비 이상 후보 탐지를 결합한 FEMS 데이터 인사이트 서비스.
- 피해야 할 것: 독일 Honda 시설 자체를 최종 서비스 대상으로 오해하게 만드는 구성, 고장을 확정 진단하는 것처럼 보이는 표현.

### 발표 대본 초안

본 프로젝트는 고해상도 EMS 데이터를 활용해 피크 위험 예측, 계량기 품질 검증, 설비 이상 후보 탐지를 결합한 FEMS 데이터 인사이트 서비스를 검증합니다.

분석 대상은 전력 소비, 냉난방 설비, PV·CHP 발전, 기상 조건, 계량기별 부하 데이터입니다. 이 데이터를 기반으로 사업장 전체 수전 피크 위험을 예측하고, 피크 시점의 동시 고부하 설비군과 발전 상쇄 상태를 함께 확인합니다.

이상치 탐지는 먼저 계량기·데이터 품질 문제를 확인하는 순서로 접근합니다. 논문에서 정의한 issue와 알려진 계량기 문제를 기준으로 결측, zero, 급변, 중복 계량, 부호 방향, 계량기 교체 gap을 검토합니다. 이 단계에서 설명되는 이상은 데이터 품질 또는 계량기 이슈로 분류합니다.

그 이후 계량기 문제로 설명되지 않는 구간에서 정상 관계를 벗어나는 residual이 반복되면, 이를 설비 운영·점검 후보로 분류합니다. 이 결과는 현장 확인이 필요한 후보로 설명하고, 고장 확정 표현은 사용하지 않습니다.

최종적으로는 예측 모델, 이상탐지, 피크 관리, LLM 기반 질의·요약 기능을 연결해 한국 제조업 현장에 적용 가능한 스마트 에너지 관리 시스템의 가능성을 확인합니다.

### 슬라이드 본문 후보

- 목표: EMS 데이터를 활용한 FEMS 피크·설비 진단형 데이터 인사이트 서비스 검증
- 입력: 전력, 냉난방, PV·CHP, 기상, 계량기별 부하 데이터
- 분석 흐름: 피크 위험 예측 → 동시 고부하 설비군 확인 → 계량기·데이터 품질 검증 → 설비 운영·점검 후보 도출
- 이상치 해석: 계량기·데이터 issue를 먼저 분리하고, 설명되지 않는 residual을 설비 이슈 후보로 검토
- 적용 방향: 한국 제조업 FEMS 적용 가능성 검증, 독일 EMS 데이터는 실증용 proxy로 사용

## 5. 데이터 구조 및 분석 범위

### 슬라이드 역할

사용한 데이터가 무엇인지, 어디서 가져왔는지, 어떤 분석 기능에 사용할 것인지 먼저 정리합니다. 이후 DB 구조와 계량기 구조는 이 데이터 설명을 보조하는 근거로 사용합니다.

### 디자인 메모

- 핵심 이미지: Figure 1 `figure 1.png` — Honda EMS 계량기 구조 이미지, Figure 2 `figure 2.png` — EMS DB ERD.
- 권장 구조: 상단에는 수집 데이터 개요 표, 하단에는 대표 테이블 필드 예시와 계량기 구조 그림.
- 시각 요소: `데이터 출처 → 수집 대상 → 사용 예정 기능`을 먼저 보여주고, DB 필드는 작은 예시 표로 처리.
- 핵심 강조: 데이터의 출처·저작권·활용 목적을 먼저 명확히 하고, ERD/적재 로직은 필요 시 보조로 제시.
- 피해야 할 것: 적재 script 세부 구현 설명, 전체 ERD를 크게 넣어 데이터 출처 설명을 가리는 구성.

### 발표 대본 초안

본 프로젝트의 주 데이터는 Honda R&D Europe EMS 공개 데이터셋입니다. 독일 Offenbach 소재 Honda R&D Europe 시설에서 수집된 전기, 열, 냉방, 기상 계측 데이터이며, Nature Scientific Data 2025 논문과 Dryad 공개 데이터셋을 근거로 사용합니다.

이 데이터는 에너지 소비 패턴 분석, 이상탐지, 에너지 사용량 예측, 보고 지표 산출, 대화형 분석 기능 검증에 사용합니다. 특히 전력, 냉난방, PV·CHP, 기상, 계량기별 부하가 함께 포함되어 있어 FEMS 피크·설비 진단형 분석 흐름을 검증하는 데 적합합니다.

보조 데이터 후보로는 한국지역난방공사 열사용량 데이터가 있습니다. 이 데이터는 국내 지역난방 열사용량 패턴 분석과 외부 비교 분석에 활용할 수 있습니다. 다만 현재 발표의 핵심 실증 데이터는 Honda R&D Europe EMS 데이터로 두고, 한국지역난방공사 데이터는 국내 적용 가능성을 보완하는 비교 후보로 구분합니다.

DB 분석 기준은 PostgreSQL/TimescaleDB `ems` schema입니다. 대표 분석 테이블은 `cr_measurement_1h`이며, 측정 시각, 계량기 식별자, measurement 코드, 측정값, 원천 파일, 적재 시각을 포함합니다. 실제 분석에서는 `corrected_resampled` 계층과 `reduced_measurement_*` view를 활용합니다.

## 6. EDA 진행 내용

### 슬라이드 역할

데이터가 어떤 형태와 범위를 가지는지 먼저 보여주고, 이후 이상탐지에서 사용할 정상 범위·물리 기준을 설명합니다.

### 디자인 메모

- 핵심 이미지: 계량기 측정 변수별 정상 범위 표. 별도 이미지 파일 없이 PPT 표로 작성.

- 참고 자료: `physical_anomaly_report_260521.html` chapter 3의 물리 기준 설명.
- 핵심 강조: 이상탐지는 계량기 측정 변수의 물리적 가능 범위와 데이터 품질 기준에서 출발하며, 임의 threshold 표현은 피함.
- 피해야 할 것: 이 슬라이드에서 모델 성능이나 최종 이상탐지 결과를 먼저 말하는 구성.

### 발표 대본 초안

EDA 진행 내용에서는 먼저 계량기 측정값이 어떤 변수로 구성되어 있고, 각 변수가 어떤 물리적 범위를 가져야 하는지 확인합니다. 전력, 전압, 전류, 역률, 누적전력량처럼 계량기에서 나오는 측정값은 각각 해석 기준이 다릅니다.

이 단계의 목적은 정상 데이터와 이상 후보를 구분하기 위한 기준을 세우는 것입니다. 예를 들어 전압이나 역률처럼 물리적으로 가능한 범위가 있는 값은 해당 범위를 벗어날 때 계량기 이상, 데이터 품질 문제, 또는 설비 상태 변화 후보로 볼 수 있습니다.

따라서 EDA 진행 내용 슬라이드에서는 계량기 측정 변수별 기준 범위를 표로 제시하고, 이후 이상탐지에서 이 기준을 어떻게 활용할지 연결합니다. 이 기준은 뒤의 모델링과 설비 이상 후보 해석에서 계량기 이슈를 먼저 분리하는 근거가 됩니다.

### 슬라이드 본문 후보

- 계량기 측정 변수별 의미와 정상 범위 확인
- 전력, 전압, 전류, 역률, 누적전력량 등 주요 measurement 기준 정리
- 정상 범위를 벗어나는 값은 계량기·데이터 품질 이상 후보로 우선 분류
- 이후 resampling/분석 계층에서 남는 이상 패턴을 설비 운영·점검 후보로 검토
- 참고: `physical_anomaly_report_260521.html` chapter 3

| 측정 변수 | 의미 | 정상 범위 / 기준 | 범위 이탈 시 1차 해석 |

## 8. FEMS 방향 : 모델링 / 이상탐지

### 슬라이드 역할

EDA 이후 분석 결과를 FEMS 기능으로 어떻게 연결할지 설명합니다. 모델링은 전력소비량 예측, 이상탐지는 계량기 이슈와 설비 이슈 분리 흐름으로 정리합니다.

### 디자인 메모

- 핵심 이미지: Figure 5 `figure 5.png`, Figure 6 `figure 6.png` — 피크 이벤트와 고부하 상단 구간.
- 시각 요소: 좌측은 전력소비량 예측 모델 흐름, 우측은 계량기 이상 → 설비 이상 후보 분리 흐름.
- 참고 링크: https://www.skax.co.kr/manufacturing-spec/fems
- 핵심 강조: 모델명 나열보다 FEMS 운영 기능으로 연결되는 구조.
- 피해야 할 것: 성능지표 표와 그래프만으로 모델링 파트를 끝내는 구성.

### 발표 대본 초안

FEMS 방향은 모델링과 이상탐지 두 축으로 정리합니다. 모델링에서는 특정 기간 내 공장 전력소비량을 예측하는 방향으로 진행합니다. 현재 후보 모델은 LSTM, SVR, XGBoost이며, 24시간 입력으로 다음 1시간 전력 사용량을 예측하는 구성을 검토합니다.

이상탐지는 계량기 이슈와 설비 이슈를 분리하는 흐름으로 잡습니다. harmonized에서 resampling으로 이어지는 과정에서 논문과 이슈집에 기록된 zero, leaf, gap 등 계량기 오류를 먼저 설명합니다.

그 다음 resampling 이후에도 남는 이상 패턴은 계량기 오류가 이미 분리되었다는 가정 아래 설비 운영·점검 후보로 봅니다. 이때는 고장 확정 표현을 피하고, FEMS가 운영자에게 확인할 우선순위를 제공하는 구조로 설명합니다.

### 슬라이드 본문 후보

- 모델링: 특정 기간 내 공장 전력소비량 예측
- 후보 모델: LSTM, SVR, XGBoost
- 예측 구성: 최근 24시간 입력 기반 다음 1시간 예측 검토
- 계량기 이상: harmonized → resampling 과정에서 zero, leaf, gap 등 issue 분리
- 설비 이상 후보: 계량기 issue로 설명되지 않는 resampling 이후 이상 패턴 검토
- FEMS 연결: 피크 예측, 설비 점검 후보, 운영자 질의·요약 지원

## 9. WBS 기반 개발 로드맵 및 역할 분화

### 슬라이드 역할

프로젝트 범위를 FEMS 예측·이상탐지·LLM 에이전트·웹 서비스까지 연결되는 개발 과제로 제시합니다. 중간발표 이후에는 데이터 파이프라인, 모델, 백엔드, 프론트엔드, RAG/Agent, 자동 리포팅을 하나의 서비스 흐름으로 통합하는 계획을 제시합니다.

### 디자인 메모

- 핵심 이미지: `계획 → 데이터/인프라 → 모델 → LLM/서비스 → 통합 검증 → 최종 발표` 6단계 로드맵. 별도 파일 없이 PPT 내부 도식으로 작성.
- 시각 요소: WBS 캡처 대신 PPT 내부 타임라인으로 재구성.
- 각 단계 아래에 2~4개 핵심 작업만 배치.
- 모델링과 이상탐지는 분석 레인, FastAPI·React·DB는 서비스 레인, Orchestrator/RAG/Reporting/Critic Agent는 LLM 레인으로 색상 구분.
- 핵심 강조: 최종 산출물은 운영자가 질의·확인·리포팅까지 수행할 수 있는 서비스 프로토타입 구조로 제시.
- 피해야 할 것: 팀원 이름만 나열하는 역할표, 세부 WBS 코드 노출, 현재 작업만 반복하는 구성.

### 발표 대본 초안

현재까지는 프로젝트 주제와 데이터 구조를 확정하고, Honda EMS 데이터를 기반으로 EDA와 분석 방향을 정리했습니다. 이후 작업은 데이터 처리, 모델 개발, 서비스 구현, LLM 에이전트 연결을 병렬로 진행한 뒤 하나의 FEMS 프로토타입으로 통합합니다.

먼저 요구사항 정의서와 WBS를 기준으로 개발 범위를 고정하고, 데이터 전처리 파이프라인과 PostgreSQL·TimescaleDB·Redis 기반 저장 구조를 구성합니다. 그 위에 FastAPI 백엔드와 React 프론트엔드의 기본 기능을 구현해 예측값, 이상 후보, 리포트 결과를 서비스 화면에서 확인할 수 있게 합니다.

분석 모델 측면에서는 이상탐지 모델과 예측 모델을 함께 개발합니다. 이상탐지는 계량기 이슈, 데이터 품질 이슈, 설비 운영·점검 후보를 단계적으로 분리하는 구조로 가져가고, 예측 모델은 XGBoost, SVR, LSTM 계열을 중심으로 전력 사용량과 피크 위험을 예측하는 방향으로 검증합니다.

LLM 연결은 Orchestrator, Anomaly Agent, Reporting Agent, RAG Agent, Critic Agent로 나누어 구현합니다. RAG에는 프로젝트 문서, 데이터 정의, 분석 결과, 이상탐지 기준을 연결하고, 챗봇 인터페이스에서 운영자가 피크 원인, 설비 후보, 데이터 품질 이슈를 질의할 수 있도록 구성합니다. 마지막으로 자동 리포팅과 end-to-end 시연 시나리오를 연결해 최종 발표에서 서비스 흐름 전체를 보여주는 것을 목표로 합니다.

### 발표 대본 초안

남은 과제는 크게 데이터 신뢰도, 모델 검증, LLM 연결, 서비스 통합 네 가지로 정리합니다.

먼저 데이터 측면에서는 Honda EMS 데이터의 계량기 구조, 결측, zero, gap, 부호 방향, 계량기 교체 구간을 더 명확히 정리해야 합니다. 이 기준이 정리되어야 이상탐지 결과를 설비 문제로 바로 확대 해석하는 것을 방지하고, 계량기 이슈와 데이터 품질 이슈를 먼저 분리할 수 있습니다.

모델 측면에서는 예측 모델과 이상탐지 모델의 검증 기준을 확정해야 합니다. 예측 모델은 전력 사용량과 피크 위험 예측을 중심으로 XGBoost, SVR, LSTM 계열을 비교하고, 이상탐지는 계량기 이슈, 데이터 품질 이슈, 설비 운영·점검 후보를 단계적으로 분리하는 방식으로 정리합니다.

서비스 측면에서는 PostgreSQL·TimescaleDB·Redis, FastAPI, React, 챗봇 인터페이스를 연결해야 합니다. LLM 측면에서는 RAG Agent, Anomaly Agent, Reporting Agent, Critic Agent의 역할을 분리하고, 분석 결과를 근거 기반 응답과 자동 리포트로 연결하는 작업이 남아 있습니다.

마지막으로 통합 테스트와 시연 시나리오를 구성해야 합니다. 최종 발표에서는 사용자가 질문을 입력하고, 시스템이 관련 데이터와 분석 근거를 찾아 예측 결과, 이상 후보, 리포트 요약을 제공하는 흐름을 보여주는 것이 목표입니다.

### 발표 시 강조할 해석 경계

- 이상탐지 결과는 설비 점검 후보로 제시합니다. 고장 확정 표현은 사용하지 않습니다.
- Honda EMS 데이터는 실증용 proxy이며, 최종 적용 방향은 한국 제조업 FEMS입니다.
- 피크 비용 해석은 수요요금·피크 리스크 관점의 proxy입니다. 총 전기요금 전체로 확대 해석하지 않습니다.
- LLM 응답은 모델 결과와 문서 근거를 요약하는 운영 지원 기능으로 설명합니다.

## 11. 예상 결과 목표

### 슬라이드 역할

최종 발표에서 보여줄 산출물을 한 장으로 묶어 제시합니다. 분석 결과, 모델 결과, LLM Agent, 웹 서비스 화면, 자동 리포팅이 하나의 FEMS 운영지원 프로토타입으로 연결된다는 점을 정리합니다.

### 디자인 메모

- 핵심 이미지: Figure 7 `figure 7.png`, Figure 8 `figure 8.png` — 요금 분리 추정과 피크 절감 시나리오. 서비스 통합 구조는 PPT 내부 도식으로 보조.
- 시각 요소: `데이터 계층 → 분석·모델 계층 → Agent 계층 → 서비스 화면·리포트` 4단 구조.
- 핵심 강조: 최종 목표는 분석 결과와 운영 지원 가능성 검증.
- 피해야 할 것: 실제 상용 시스템 완성처럼 과장하는 표현, 모델 성능만 강조하는 구성.

### 발표 대본 초안

최종 결과 목표는 FEMS 피크·설비 진단형 데이터 인사이트 서비스의 프로토타입을 완성하는 것입니다.

첫 번째 산출물은 데이터 계층입니다. Honda EMS 데이터를 전처리해 PostgreSQL·TimescaleDB에 적재하고, 분석에 필요한 테이블과 view를 정리합니다. Redis는 서비스 응답과 중간 결과 관리에 활용하는 방향으로 구성합니다.

두 번째 산출물은 분석·모델 계층입니다. EDA 결과를 바탕으로 전력 사용량과 피크 위험을 예측하고, 계량기 이슈와 데이터 품질 이슈를 먼저 분리한 뒤 설비 운영·점검 후보를 도출합니다.

세 번째 산출물은 LLM Agent 계층입니다. RAG Agent는 요구사항 정의서, 데이터 정의, 분석 결과, 이상탐지 기준을 검색하고, Orchestrator는 사용자 질문을 적절한 Agent로 라우팅합니다. Reporting Agent는 분석 결과를 요약하고, Critic Agent는 응답의 근거성과 해석 경계를 점검합니다.

네 번째 산출물은 서비스 화면과 시연 흐름입니다. React 대시보드와 챗봇 인터페이스에서 예측 결과, 이상 후보, 근거 문서, 자동 리포트를 확인하는 end-to-end 흐름을 최종 발표에서 보여주는 것을 목표로 합니다.

### 슬라이드 본문 후보

| 계층 | 최종 산출물 | 발표 시 보여줄 내용 |
|---|---|---|
| 데이터 계층 | 전처리 파이프라인, PostgreSQL·TimescaleDB, Redis | 정제 데이터와 분석용 테이블 구조 |
| EDA 계층 | 계량기 기준 범위, 상관관계, STL, Sliding Window | 데이터 특성과 이상 후보의 근거 |
| 예측 모델 | 전력 사용량 예측, 피크 위험 예측 | 예측 결과와 모델 비교 |
| 이상탐지 | 계량기 issue, 데이터 품질 issue, 설비 점검 후보 | 3단계 이상탐지 결과 |
| LLM Agent | Orchestrator, RAG, Anomaly, Reporting, Critic Agent | 근거 기반 질의응답과 자동 요약 |
| 서비스 계층 | FastAPI, React, 챗봇 UI, 자동 리포트 | end-to-end 시연 화면 |
| 문서화 | README, 발표자료, 시연 시나리오 | 최종 제출물 |

### 최종 시연 목표

1. 사용자가 챗봇에 피크 위험 또는 이상 후보를 질의합니다.
2. 시스템이 관련 데이터, 모델 결과, 문서 근거를 검색합니다.
3. Agent가 예측 결과와 이상 후보를 요약합니다.
4. Critic Agent가 해석 경계와 근거 누락을 점검합니다.
5. React 화면 또는 자동 리포트에서 결과를 확인합니다.

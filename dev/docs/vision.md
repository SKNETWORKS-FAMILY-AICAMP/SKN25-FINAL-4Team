# TTF-FMS — 서비스 방향성

> **한 줄 정의**
> "센서 증설 없이 기존 전기·에너지 계측만으로 설비를 진단하는 AI 코파일럿."
> 물어보면 답하고, 이상이 생기면 먼저 말을 걸며, 무엇을·왜·언제 조치할지까지 설명한다.

> **방향 전환(2026-06)** — FEMS(에너지 관리)에서 **CMS(설비 상태감시·예지보전)** 로 무게중심 이동.
> 이상탐지·설비 진단이 주력, 에너지(예측·요금)는 보조. AI가 가치를 더하는 곳이 "진단·해석·결정"이라는 판단.

---

## 1. 시장이 가진 문제

설비 상태감시(CMS)·예지보전 시장은 **물리 센서 증설을 전제**로 한다.
- 진동·온도·압력 센서를 설비마다 달아야 함 → 도입 비용·인프라 부담이 큼.
- 탐지/알람은 주지만, **"왜 이상한지·무엇을 할지"는 사람의 판단**에 달려 있음.
- 중소 제조기업엔 전문 분석 인력이 없어, 데이터가 있어도 행동으로 이어지지 않음.

---

## 2. TTF-FMS가 하는 것

**"데이터 → 진단 → 결정"의 마지막 한 걸음을 AI가 채운다. 그것도 이미 있는 데이터로.**

| 기존 CMS/모니터링 | TTF-FMS |
|---|---|
| 진동 센서로 "베어링 이상" 알람 | **기존 전기 계측(전압·전류·역률)** 으로 "히트펌프 COP 저하" 감지 |
| 탐지 정확도 수치·대시보드 | "왜 그런가 → 원인 → 오늘 할 조치"를 **LLM이 설명** |
| 운영자가 알람 보고 직접 판단 | "이상한 설비 클릭 → AI 진단 → 작업지시 생성"까지 한 흐름 |
| 정적 리포트 | **대화로 물어보고, 챗봇이 작업지시·시뮬까지 실행** |

**핵심 차별점**: 경쟁사는 센서 증설이 전제 / 우리는 **기존 데이터 + LLM 코파일럿**. 데이터 니치(전기·성능 시그니처) + AI 깊이(진단·대화·행동).

---

## 3. 핵심 기능 — CMS 4대 축 + AI 코파일럿

### 핵심 (CMS)
1. **설비 상태 감시** — 설비별 헬스 스코어(노출시간 정규화) + 상태등급 + 현재 지표
2. **AI 고장 원인 진단** — 이상 이력 + **전기 시그니처(3상 불평형·역률·주파수)** + 도메인 지식 → LLM 원인·근거·조치
3. **예지보전** — COP·이상 발생률 추세 외삽으로 "현 추세면 N개월 후 기준치 도달" (추세 기반·참고용)
4. **정비 작업지시** — 진단 → 작업지시 → 진행/완료 → 조치 이력 (학습 루프)

### AI 코파일럿
- **대화형 + 에이전트** — 자연어 질의(LangGraph) + 실제 행동(작업지시 생성·시뮬 제어) + 현재 설비 컨텍스트 인지 + 알림→자동 분석
- **적응형 학습** — 권고 outcome 누적으로 재랭킹·신뢰도

### 운영 보조 (에너지)
- 수요 예측(VMD-LSTM+XGBoost) · 제어/최적화 권고 · 목표 요금 · 월간/일일 보고서

---

## 4. 차별화 포인트

1. **데이터 니치** — 센서 증설 없이 기존 전기·에너지 계측만으로 설비 진단 (도입 부담 없음)
2. **AI 네이티브 진단** — 탐지(ML)는 팀 모델, 그 위에서 LLM이 신호 근거로 원인·조치 설명
3. **행동하는 코파일럿** — 답변만이 아니라 작업지시 생성·시뮬 제어까지 실행
4. **성장하는 시스템** — 조치 결과를 학습해 다음 권고에 반영
5. **이상→진단→정비 폐루프** — 한 화면 흐름으로 통합

## 6. 기술 분담

- **keun**: FastAPI 라우터·LangGraph 에이전트·React 프론트·도커·CMS 전 기능
- **팀원**: ML 모델 — VMD-LSTM(예측)·잔차+Isolation Forest(이상탐지). 인터페이스 계약은 `docs/ML_INTERFACE.md` 참고.
- 원칙: ML 내부 로직은 팀원, 인터페이스(라우터·에이전트 연동)만 keun이 관리. CMS 전 기능이 `anomaly_results`를 소비하므로 이상탐지 모델 교체 시 자동 개선.

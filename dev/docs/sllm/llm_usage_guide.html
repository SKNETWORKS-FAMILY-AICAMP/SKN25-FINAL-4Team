1. 전체 그림 — sLLM이 하는 일과 하지 않는 일

핵심 원칙: sLLM은 계산하지 않는다. 설명한다.
백엔드가 DB·ML로 이미 만들어낸 결과물을 운영자가 이해할 수 있는 한국어로 변환하는 것이 유일한 역할이다.

sLLM이 하지 않는 것

작업실제 담당
이상 탐지LSTM + IsolationForest + 통계 모델
전력 예측v84 앙상블 (LSTM×6 + CatBoost + LightGBM)
KPI 계산DB 집계 쿼리
전기 서명 계산전압·전류·역률 실측값 DB 직접 계산

sLLM이 하는 것

질문sLLM 역할
"이상 원인이 뭐야?"탐지 결과 + 센서값 → 원인·조치 설명
"보고서 써줘"KPI 수치 → 서술 문장 생성
"예측 해석해줘"ML 수치 → 운영 조언
채팅 일반 질문RAG 문서 + 실측값 → 답변
왜 이렇게 나눴나?
12B짜리 소형 모델로도 충분한 품질을 내려면 LLM이 "어려운 것"을 안 하면 된다. LLM에게 "원시 센서 수천 행을 보고 이상을 찾아라"고 시키면 틀린다. 반면 "이 데이터를 보고 설명해라"는 잘 한다. 백엔드가 어려운 계산을 미리 끝내고 LLM에게는 글쓰기만 맡기는 구조다.

3. 코드 구조 — 어디서 어떻게 쓰이나

단일 진입점 원칙

모든 LLM 호출은 반드시 한 곳을 거친다. 10곳 전부 아래 함수를 호출한다.

# backend/src/agents/llm_client.py

def chat(messages, max_tokens=1024, fast=False, thinking=None):
    model = LLM_MODEL_FAST if fast else LLM_MODEL
    # fast=True  → EXAONE (의도분류용, temperature=0.1)
    # fast=False → Gemma4 (분석·보고서용, temperature=0.3)

    if thinking is None:
        thinking = not fast   # 기본값: quality→ON, fast→OFF

    payload = {
        "model":      model,
        "think":      thinking,
        "keep_alive": -1,       # 모델 영구 적재
        "options": {"num_ctx": 8192, ...}
    }
이 덕분에 .env의 모델명 두 줄만 바꾸면 전체 시스템 모델이 교체된다. 코드 수정 불필요.

4. 요청 흐름 — 순서대로

경로 A: 채팅 질문 (가장 일반적인 경로)

① 프론트엔드 사용자가 채팅창에 질문 입력 → POST /chat/stream ② chat.py — _invoke_graph() 히스토리 최근 10턴을 lc_messages로 변환 LangGraph 그래프 실행 시작 ③ orchestrator — classify_intent() ┌─ 1단계: 키워드 룰 (LLM 없음, 즉시) │ "이상탐지" → anomaly │ "보고서" → report │ "주식" → off_topic (즉시 거절, LLM 없음) │ 매칭 성공 → ④ 바로 이동 │ └─ 2단계: 룰 실패 시 EXAONE 호출 ← LLM #1 fast=True, max_tokens=10 "anomaly / rag / report / forecast / cms / off_topic" 반환 ④ 의도별 에이전트 분기 ├── anomaly → DB 이상 조회 + 센서값 → Gemma4 호출 ← LLM #2 ├── rag → pgvector 검색 + 실측값 → Gemma4 호출 ← LLM #2 ├── report → KPI 집계 → Gemma4 호출 ← LLM #2 ├── forecast → v84 앙상블 추론 → Gemma4 호출 ← LLM #2 ├── cms → DB 조회 + 포맷팅 → LLM 없음 └── off_topic→ 거절 문자열 → LLM 없음 ⑤ critic_node() 문자열 치환만 수행 (한전→독일 공공 전력망 등) LLM 없음 ⑥ 응답 반환 단어 단위 SSE 스트리밍으로 프론트에 전송

채팅 1회 LLM 호출 횟수

키워드 룰 성공1번 (에이전트 1회)
키워드 룰 실패2번 (의도분류 + 에이전트)

5. 성능 향상 기법 — 어떻게 품질을 올렸나

12B 소형 모델로 품질을 높이기 위해 쓴 기법 10가지.

1
데이터 선주입 가장 중요

LLM에게 질문만 던지는 게 아니라, 백엔드가 먼저 필요한 데이터를 모두 모아서 프롬프트에 담아 보낸다. LLM이 추론·환각으로 수치를 만들어내지 않고 제공된 데이터만 인용한다.

# anomaly_agent.py — LLM 호출 전 데이터 준비
anomalies = _fetch_anomalies(...)           # DB 이상 결과 조회
anomalies = _enrich_with_sensors(...)       # 이상 시각 센서값 추가
type_counts = _count_anomalies_by_type()    # 유형별 건수 집계

# 완성된 데이터를 프롬프트에 담아 LLM 호출
answer = llm_chat(f"이상 결과:\n{anomaly_block}\n센서값:\n{sensor_block}\n...")
2
Few-shot 프롬프팅

이상적인 입출력 예시를 프롬프트에 함께 넣어 출력 형식과 품질을 고정한다.

위치few-shot 개수목적
cms.py 설비 진단2개계절 오진단 방지 + 발전 설비 역률 오진단 방지
anomaly_agent.py1개분석 출력 형식(핵심요약/유형분석/즉시조치) 고정
report.py 일일 보고서2개SUMMARY/ACTIONS 형식 강제
report.py 월간 트렌드1개수치 인용 방식 예시 제공
3
RAG (Retrieval-Augmented Generation)

RAG Agent가 질문에 답하기 전에 pgvector로 관련 문서를 검색해 컨텍스트에 포함시킨다. 계량기 URN이 질문에 있으면 DB에서 최신값·평균·범위를 직접 조회해 주입한다.

# rag_agent.py
state.doc_context = search_documents(question)         # pgvector top-5 검색
state.meter_facts = lookup_meter_measurements(question) # 계량기 실측값 DB 조회

# 검색 결과 + 실측값을 프롬프트에 포함
prompt = build_prompt(state)
answer = llm_chat(prompt, thinking=False)
4
도메인 지식 주입

모델 사전학습 데이터에 없는 공장 특화 지식을 knowledge/domain_knowledge.py에 정리해 모든 프롬프트에 삽입한다.

지식 항목내용없으면 발생하는 문제
계절 정상 COP여름 외기온 30°C+ 시 COP 1.7~2.0 정상여름 COP 1.85를 이상으로 오진단
CHP 겨울 효율열 수요 증가 시 전기 효율 ±3~5%p 감소 = 정상겨울 CHP 효율 저하를 고장으로 오진단
발전 설비 역률PV·CHP 역률 음수/저값 = 역송 정상역률 -0.95를 고장으로 오진단
게이트웨이 장애 구간특정 기간 데이터가 인공 보정값임보정 데이터를 실제 이상으로 오판
Regime 이벤트PV 증설·COVID·CHP 변경 등 시설 변화 이력구조적 변화를 이상으로 오해
5
thinking 모드 제어

Gemma4 12B는 답하기 전에 내부 추론 과정(thinking)을 수행한다. 작업 성격에 따라 켜고 끈다.

# thinking=True: 복잡한 분석 (기본값, 속도 느리지만 품질↑)
llm_chat(prompt, thinking=True)    # 진단·보고서·이상분석

# thinking=False: 단순 설명 (속도↑)
llm_chat(prompt, thinking=False)   # RAG 일반 답변

# fast=True: EXAONE으로 전환 + thinking 자동 OFF
llm_chat(prompt, fast=True)        # 의도 분류 (max_tokens=10)
6
출력 형식 강제

프롬프트에 정확한 출력 형식을 지정해 파싱 안정성을 높인다. 형식 강제가 없으면 LLM이 매번 다른 구조로 답해 백엔드 파싱이 깨진다.

# report.py — 일일 보고서 형식 강제
"다음 두 섹션을 정확히 아래 형식으로 출력하세요. 다른 텍스트 없이.

---SUMMARY---
(3~4문장)

---ACTIONS---
(체크리스트)"

# 백엔드에서 구분자로 split 후 각각 프론트에 전달
parts   = raw.split("---ACTIONS---", 1)
summary = parts[0].replace("---SUMMARY---", "").strip()
actions = parts[1].strip()
7
환각 방지 명시 지시

LLM이 없는 수치를 만들어내는 것을 명시적으로 금지한다.

# reporting_agent.py
"위 KPI 데이터에 없는 수치를 만들어내지 마세요. 수치가 없으면 '데이터 없음'으로 표기하세요."
"하나의 완성된 보고서만 작성하세요. 대안, 다른 버전, 예시 비교를 절대 제시하지 마세요."

# cms.py
"제공되지 않은 수치를 추론으로 생성하지 마세요."

# anomaly_agent.py
"이상 발생 시각과 센서 수치는 반드시 위 데이터에서 직접 인용하세요."
8
모델 영구 적재 (keep_alive)

Ollama는 기본적으로 일정 시간 후 모델을 메모리에서 내린다. 재요청 시 다시 로딩하면 1~2분 지연이 생긴다. keep_alive: -1로 영구 적재해 재로딩 대기를 제거했다.

payload = {
    "keep_alive": -1,  # 모델을 메모리에서 내리지 않음
    ...
}
9
진단 결과 캐싱

같은 설비를 같은 날 다시 진단 요청하면 LLM 재호출 없이 캐시된 결과를 반환한다.

# cms.py
cache_key = f"{eq_id}|{window_days}|{anchor.date().isoformat()}"
if cache_key in _diag_cache:
    return _diag_cache[cache_key]   # LLM 호출 없이 바로 반환
10
LLM 실패 시 폴백

LLM 호출이 실패해도 서비스가 중단되지 않도록 룰 기반 폴백이 준비되어 있다.

# cms.py
try:
    diagnosis = llm_chat(...)         # LLM 진단 시도
    llm_used = True
except Exception:
    diagnosis = _fallback_diagnosis(eq, total, by_type)  # 룰 기반 폴백
    # 이상 건수와 유형 기반 템플릿 진단문 생성

6. 에이전트별 상세

🧭
의도 분류 — Orchestrator
orchestrator.py:157 · EXAONE 7.8B · fast=True · max_tokens=10

사용자 질문을 6개 의도로 분류해 적절한 에이전트로 라우팅한다. 대부분은 키워드 룰이 처리하고, LLM은 룰이 실패한 경우에만 호출한다.

단계처리LLM
1단계키워드 정규식 매칭 (anomaly/report/cms/forecast/off_topic)없음
2단계 (폴백)EXAONE에게 의도 분류 요청 (단 10토큰)EXAONE

의도: anomaly / rag / report / forecast / cms / off_topic

💬
채팅 답변 — RAG Agent
rag_agent.py:178 · Gemma4 12B · thinking=False · max_tokens=1024

개념 설명, 계량기 실측값 조회, 일반 에너지 질문에 답한다.

사전 처리내용
pgvector 문서 검색top-5 관련 청크를 컨텍스트에 포함
계량기 실측값 조회질문에 URN(V.Z84 등)이 있으면 DB에서 최신값·평균·범위 직접 주입
도메인 지식DOMAIN_KNOWLEDGE_PROMPT 항상 포함

thinking=False: 단순 설명 용도이므로 thinking 비활성화 → 응답 빠름

🚨
이상 원인 분석 — Anomaly Agent
anomaly_agent.py:441 · Gemma4 12B · thinking=True · max_tokens=1024

8. 인프라 — RunPod 구성

왜 RunPod인가? 회사 설비 데이터를 OpenAI 등 외부 API로 보낼 수 없다(보안). 로컬 CPU로는 12B 모델 추론이 너무 느리다(수 분 단위). RunPod RTX 3090 (24GB VRAM)에서 두 모델 동시 적재 가능.

RunPod 구성

RunPod RTX 3090 (24GB VRAM)
└── Ollama 서버
    ├── gemma4:12b       ~8GB VRAM
    └── exaone3.5:7.8b  ~5GB VRAM
    합계 ~13GB / 24GB 사용

접속: https://{pod-id}-11434.proxy.runpod.net/v1

Pod 재생성 시 복구 (2개 명령)

# RunPod 내부
ollama pull gemma4:12b
ollama pull exaone3.5:7.8b

# .env — URL만 교체
OLLAMA_URL=https://{새pod-id}-11434...

docker compose restart backend
바꿀 것: URL 1줄
그대로 유지: 모든 프롬프트, few-shot, 도메인 지식, 듀얼 모델 라우팅, 평가 결과 전부

9. 성능 병목

작업소요 시간위치
LSTM 추론 (이상탐지/예측)0.5~2초백엔드 CPU
DB 쿼리0.1~0.5초DB 서버
sLLM 호출 (thinking=False)5~10초RunPod GPU
sLLM 호출 (thinking=True)15~30초RunPod GPU ← 병목
체감 응답 대기의 80~90%가 sLLM 대기다. CPU 사양을 높여도 체감 속도 개선은 제한적이다. RunPod GPU 사양과 안정성이 훨씬 중요하다.
